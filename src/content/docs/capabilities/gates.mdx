import { Aside } from '@astrojs/starlight/components';

Gates are hooks wired into the agents' tool calls. One property holds for eighteen of
the nineteen, and two more describe when a gate is on. The exception is
`cloudcare-fence` (0.12.3), which **fails closed**: see
[The CloudCare fence](#the-cloudcare-fence-cloudcare-fence).

- **Four safe hooks are armed for you.** `mission-inject`, `mission-turn-recorder`,
  `session-context` and `update-notify` can't block anything: they inject text or
  record a receipt. Every install and every `kiroctl update` arms them (see
  [The four safe hooks](#the-four-safe-hooks-are-armed-by-default)).
- **`mission-state-protect` is armed by default too (0.11.0, beta).** It does refuse, but
  only an agent's edit of mission state and a mission cleared before its audit. See
  [`mission-state-protect` is armed by default](#mission-state-protect-is-armed-by-default).
- **Eight hooks are always on, and the other blocking gates are inert until armed.**
  The always-on hooks are `telemetry-emit`, `mc-signin-gate` and `mc-session-health`,
  which are always on because telemetry and the Mission Control sign-in are mandatory
  RevStar policy (see [Telemetry](/capabilities/telemetry/)); `mobile-guard` and
  `mobile-sweep`, which are always on because Mobile Next device minutes are metered
  and shared (see [Mobile app QA](/workflows/mobile-qa/)); `mission-pause`, the
  emergency brake (see [Stopping a mission](/workflows/missions/#stopping-a-mission)); and
  `broker-merge-gate` (0.10.0, beta), which registers a lane mission's merges with the broker and does nothing outside a
  lane (see [Missions in a lane](/workflows/missions/#missions-in-a-lane)); and
  `tool-watchdog` (0.11.0, beta), which ends a stuck tool call (see
  [The stuck-tool watchdog](#the-stuck-tool-watchdog)).
  Every other gate does nothing until a `.enabled` flag file exists for it. Arm those
  globally or per project:

  ```sh
  touch ~/.kiro/gates/<name>.enabled          # everywhere
  touch <project>/.kiro/gates/<name>.enabled  # this project only
  ```

  To arm every gate in one step, run the installer with `--arm-all` (`install.sh`) or
  `-ArmAll` (`install.ps1`). **From 0.11.0 that includes `ado-receipt-gate`.** It is
  still off by default: a plain install and `kiroctl update` do not arm it, and a gate with a
  `.disabled` file stays off.

- **`cloudcare-fence` (0.12.3) is on only while a CloudCare `report` mission runs.** It has no flag file and no
  off-switch, and with no report mission it does nothing. See [The CloudCare fence](#the-cloudcare-fence-cloudcare-fence).

- **Fails open.** (All but `cloudcare-fence`.) A gate that errors or isn't armed never blocks the call it
  would otherwise inspect. An armed gate that doesn't fire is worse than no
  gate at all, because it's trusted — arm one at a time and verify it.

<Aside type="caution">
An armed `block` gate does exactly what its row says and nothing more. If a
gate should be stopping something and isn't, confirm the flag file exists
before assuming the rule doesn't apply.
</Aside>

## The nineteen gates

| Gate | Trigger | Kind | What it does |
| --- | --- | --- | --- |
| `mission-inject` | Session start | inject | Re-injects the active mission so it survives context compaction. Armed by default. |
| `mission-turn-recorder` | Prompt submitted, turn end | inject | Writes the turn receipt the mission chat's continue hook reads (a cleared mission emits a terminal stop) and times each turn, which is where a mission's [autonomous hours](/capabilities/telemetry/#autonomous-hours) come from. Armed by default. |
| `mission-state-protect` | write / shell | block | Refuses hand-edits of mission state, receipts, gate flags (`.enabled` and `.disabled`), the scoped QA record and the QA close-receipts, and un-audited mission clears. Armed by default from 0.11.0. `mission-state.js` enforces the clear rule itself too, so it holds with the gate off. During an active mission it also refuses an agent's edits to a lane repo's `.mission-lane` file and to `scripts/broker/registry.json` (0.11.0, beta): they hold the lane's protected branches and lease, so a person edits them outside a mission. Reading is fine, the `.mission-lane.lane-1` / `.lane-2` templates are not guarded, and with no active mission both are ordinary files. Its stop-control half is **always on**: it also refuses an agent's attempt to touch the pause and stop-all files, the mission index, a hook's `.disabled` opt-out, the app's token log and mission API, and `kiroctl missions` (except `list`). **0.12.0.** It also refuses an agent writing `.kiro-mission*.approval.json`, running `kiroctl missions approve` or `decline`, and running `--clear --estimate-declined`: the answer to a QA mission's estimate is a person's. **0.12.3.** While a **resolve chat** is open for a project it also refuses writes to that project's access contract, plan files and grill receipts, and it protects the resolve markers ([below](#the-resolve-chat-guard)). See [below](#what-mission-state-protect-refuses-even-when-unarmed). |
| `qa-render-gate` | fetch | block | Forces a real-browser render during QA instead of accepting a fetch as a visual check. A `mobile` run is not exempt: web pages still need the browser. |
| `qa-report-gate` | write | block | Refuses a QA report missing `WORKS` + `MATCHES INTENT` verdicts (each with `method: live\|inspection\|code`), render evidence, a real coverage receipt file (full runs), or the adversarial-pass receipt (runs with change items); and any "PASS with note". For a run marked `mobile`, also refuses a report with no fresh device screenshot, a device still booked, a created test account with no cleanup, or no build file id and commit. **0.11.0.** The heading test (a body that opens like a QA report) applies only to `.md`, `.markdown`, `.txt` and extensionless files, never to code such as `.sh`, `.js` or `.py`; a path under `qa-reports/` is still judged as a report. **0.12.0.** Two file names under `qa-reports/` are exempt, because each is an input or a catalog, not a QA report: the bug document `qa-reports/fix-bugs-<mission-id>.md` that `/fix-bugs ado=` writes, and the regression catalog `qa-reports/ci-regression-candidates.md`. Neither needs verdict lines or a waiver. Any other file name there is still judged as a report. |
| `git-protect-gate` | shell | block | Refuses direct commit/merge/push to protected branches and `--no-verify`; allows `gh pr`. **0.11.0.** Also checks a PR before `gh pr merge` ([below](#the-merge-check-git-protect-gate)). In a repo in a Mission Control lane it also protects the lane file's `branch_base` and `pr_base` (0.10.0, beta). **0.11.0.** Repo paths are compared by real path, so a linked repo is one lane entry. |
| `ado-receipt-gate` | shell | block | Refuses opening a PR (`gh pr create` / `glab mr create` / `az repos pr create`) for ADO-bound work — a `feat/<id>-*` branch — until the item's status / assignee / comment update is recorded as a receipt. Disarmed by default; fails open (any uncertainty or error allows the PR); fires only on ADO-bound branches. **0.11.0.** The app's Settings → Gates has a checkbox for it ([below](#the-ado-receipt-gate-in-the-app)). |
| `reuse-before-create-gate` | new-file write | soft | Warns once about a duplicate of an existing owner, then relents. |
| `session-context` | Session start | inject | Injects a git snapshot into context. Armed by default. |
| `update-notify` | Session start | inject | Reminds you when a newer version is available; rate-limited, fails open. Armed by default. |
| `telemetry-emit` | read | always-on | Emits `skill_run` and opportunistically flushes the adoption-telemetry spool. Mandatory RevStar policy, not arm-gated. Never blocks; fails open. See [Telemetry](/capabilities/telemetry/). |
| `mc-signin-gate` | prompt submit (`dev`, `coder`, `scout`) | always-on block | Refuses the prompt until you are signed in to Mission Control. See [below](#mission-control-sign-in). |
| `mc-session-health` | Session start (`dev`) | always-on inject | Checks the Mission Control connection locally, starts the background repair, and notes only *changes* that need you. See [Telemetry → Self-check](/capabilities/telemetry/#self-check-and-repair). |
| `mobile-guard` | Mobile Next tool calls (`dev`, `coder`) | always-on block | Guards every Mobile Next call: refuses a production or unprovable build, an allocation with no stored file, an empty or unreadable balance, and a run past its minute cap (80% one-time warning, 100% forced release). Idle devices are released outside a QA pass. Fails closed only on a booking it cannot budget-check. See [Mobile app QA](/workflows/mobile-qa/#safeguards-and-costs). |
| `mobile-sweep` | Session start (`dev`) | always-on inject | Releases devices a crashed session left booked and reports any it could not release or could not identify. Never blocks. |
| `mission-pause` | Every tool call (`dev`, `coder`, `scout`) | always-on block | The emergency brake. Refuses every tool call in a session whose mission a person paused, and in every session on the machine while **Stop all agents** is on. Lets only the `goal` completion tool through. Fails open on its own errors. See [Stopping a mission](/workflows/missions/#stopping-a-mission). |
| `broker-merge-gate` | shell (`dev`, `coder`) | always-on block | **0.10.0.** In a lane repo during a mission, registers the PR under the mission's broker lease (`add-pr`) before `gh pr merge` goes through. Refuses the merge when the broker says the mission doesn't hold the lane (naming the holder), while the mission is queued or its lane is lost, and for `gh pr merge --auto`. Lets the merge through with a warning when the broker can't be asked on a fail-open lane. Does nothing outside a lane repo or a mission. See [below](#what-broker-merge-gate-refuses). |
| `tool-watchdog` | Every tool call, pre and post (`dev`, `coder`, `scout`) | always-on | **0.11.0.** Ends a tool call that has run for 30 minutes without a result, and a chat stuck between tools after 20 minutes with no hook event and no tool process. A person can turn it off with `tool-watchdog.disabled`. See [The stuck-tool watchdog](#the-stuck-tool-watchdog). |
| `cloudcare-fence` | Every tool call (`dev`, `coder`, `scout`) | always-on block, **fails closed** | **0.12.3.** Active only while a [`report` mission](/workflows/missions/#the-report-mission-cloudcare) runs. Lets the agent reach client AWS only through `./cloudcare.sh clients\|check\|collect\|draft\|build\|render`, and locks the CloudCare repo's code. Does nothing when no report mission is active, and has no switch. See [The CloudCare fence](#the-cloudcare-fence-cloudcare-fence). |

## What `broker-merge-gate` refuses

Only in a repo in a Mission Control lane, during an active mission (see
[Missions in a lane](/workflows/missions/#missions-in-a-lane)). Each refusal starts with `BLOCKED broker-merge-gate:`.

| Refusal | Why | What to do |
| --- | --- | --- |
| `the broker refused to register PR #N under this mission's lease on <resource>: <resource> is held by <holder> …` | Another mission holds the lane. | Nothing to force. The mission re-claims at its next heartbeat and waits if queued; `node <pack>/bin/mission-broker.js status --live` shows who holds it. |
| `WAITING for lane <lane> (<resource>): held by <holder> …` | This mission is queued for the lane. | Wait. It lifts by itself when the broker grants the lane. |
| `lane <lane> (<resource>) is lost … and the re-claim was not granted` | The lease timed out or hit its hold limit, and another mission got the lane. | Wait for the re-claim. |
| `gh pr merge --auto is refused in a lane repo` | An auto-merge can land after the lease is released, so its build wouldn't be registered. | Wait for the checks, then `gh pr merge <N>` without `--auto`. |
| `could not tell which PR this merges` | A bare `gh pr merge` or a branch name, and `gh pr view` couldn't find the PR number. | Merge by number: `gh pr merge <N>`. |

When the broker can't be asked (no AWS session, unreachable, or the CLI can't start) on a fail-open lane, the merge goes
ahead with a `broker: WARNING …` line, and the PR is registered at the next heartbeat.

## The merge check: `git-protect-gate`

**0.11.0.** When `git-protect-gate` is armed, it checks the PR before every `gh pr merge`. It runs
`gh pr view --json isDraft,baseRefName,statusCheckRollup,state` with a 15-second timeout (change it with
`GIT_PROTECT_GH_TIMEOUT_MS`). It refuses the merge when:

- the PR is a **draft**;
- a check has **failed**: `FAILURE`, `CANCELLED`, `TIMED_OUT`, `ACTION_REQUIRED` or `STARTUP_FAILURE`, or a status of `FAILURE` or `ERROR`;
- a check is **pending**, unless the merge uses `--auto`;
- the PR's base is **not the mission's integration branch**. That branch is frozen at `--init`; a branch the script only guessed doesn't count. This works from a git worktree;
- the base is a **production branch** (`main`, `master`, `prod`, `production`) while a mission is active, unless that is the mission's own integration branch. Promotion to production waits until every phase is closed and the mission is cleared.

A PR with no checks counts as green. If `gh` is missing, not signed in, times out or returns something
unreadable, the merge is allowed with a one-line note. A PR that is already merged or closed is left to
`gh`. The gate follows `cd`, `bash -c` and `-R`.

The gate doesn't wait for the phase audit. In a mission the audit is the review, and it runs after the
merge. See [Phases](/workflows/missions/#phases-rules-v2).

## The ADO receipt gate in the app

**0.11.0.** The app's **Settings** drawer has a **Gates** section with an **ADO receipt gate**
checkbox: "Refuses to open a pull request (`gh pr create`, `glab mr create`, `az repos pr create`) on an
ADO-numbered branch until the ado-write skill has posted its progress comment. Off by default." The
status reads **armed**, **off by choice** or **not armed**.

- Checking the box writes `~/.kiro/gates/ado-receipt-gate.enabled`.
- Unchecking writes `ado-receipt-gate.disabled`. That is "off by choice", so `install.sh --arm-all`
  won't arm it again.
- Only a person can change it. An agent's request gets a 403.
- It shows the global flag only. A project's own `.kiro/gates` flag isn't shown.

## Kinds

- **inject** — adds context; never refuses a call.
- **block** — can refuse the tool call outright if its rule is violated.
- **soft** — warns once, then gets out of the way rather than blocking
  repeatedly on the same finding.
- **always-on** — runs without being armed. `telemetry-emit`,
  `mc-session-health` and `mobile-sweep` never refuse anything; `mc-signin-gate`
  can refuse a prompt, `mobile-guard` can refuse a Mobile Next tool call, and
  `mission-pause` refuses every tool call, but only while a person has paused a
  mission or stopped all agents.
  **0.12.3.** `cloudcare-fence` is always on too, but it only acts while a `report` mission runs, and it is
  the one gate that **fails closed**.

## The four safe hooks are armed by default

From 0.9.0, `install.sh`, `install.ps1`, the bootstrap scripts and `kiroctl update`
all arm `mission-inject`, `mission-turn-recorder`, `session-context` and
`update-notify`. Before, they were armed only with `--arm-safe`; the flag still works
and now does the same as no flag. The blocking gates stay inert until you arm them.

What changes in your sessions:

- During a mission, the mission text is re-injected at session start.
- The turn recorder times each turn. That is what gives a cleared mission its
  measured [autonomous hours](/capabilities/telemetry/#autonomous-hours). With it off,
  the clear reports no hours.
- Every session starts with a short git snapshot (`session-context`).
- You get an update reminder when a newer version is out (`update-notify`).

**Turning one off for good.** Create a file named `<name>.disabled` in
`~/.kiro/gates/`:

```sh
touch ~/.kiro/gates/session-context.disabled
```

The hook is now off by choice. Installs and `kiroctl update` never re-arm a hook that
has a `.disabled` file, even with `--arm-all`. Delete the file and run
`kiroctl update` to turn it back on. Agents can't create, change or remove a
`.disabled` file.

`kiroctl doctor` and **Settings → Diagnostics** show one row per safe hook:
*armed*, *off by choice* (what you lose, and the file to delete) or *not armed* (the
fix, usually `kiroctl update`). Diagnostics also warns when the turn recorder is armed
but the installed `dev` agent doesn't run it when a prompt is submitted. That happens
on an older pack: each turn is then timed from the previous turn's end instead of its
start.

## `mission-state-protect` is armed by default

**0.11.0.** `install.sh`, `install.ps1` and `kiroctl update` arm `mission-state-protect`
along with the four safe hooks. It has the same opt-out: a `~/.kiro/gates/mission-state-protect.disabled`
file keeps installs and updates from re-arming it, and agents can't create it. `kiroctl doctor` and
Diagnostics show it as a fifth hook row (*armed*, *off by choice* or *not armed*). The other blocking
gates (`qa-render-gate`, `qa-report-gate`, `git-protect-gate`, `reuse-before-create-gate`) stay inert
until you arm them.

What the armed gate adds to a mission: an agent can't edit the sentinel, the acceptance ledger,
receipts or gate flags by hand, and it can't clear a mission from any state but `audit` or while the
ledger is unmet. The ledger rule matches `mission-state.js`: `access-descoped:*` and `skipped:*`
criteria don't block, and an advisory mission with no ledger may clear. The script applies the same
rules with no gate armed; see [Clearing a mission](/workflows/missions/#clearing-a-mission).

## What `mission-state-protect` refuses even when unarmed

Before 0.11.0 the gate's original job, protecting mission state, needed its `.enabled` flag.
Its stop-control half never did. With or without the flag, an agent can't:

- create, change, move or delete a pause file (`~/.kiro/missions/*.paused`), the
  `~/.kiro/stop-all` file, a driver record, or the mission index in
  `~/.kiro/missions/`. Reading them (`ls`, `cat`) is fine. This holds for the
  real kiro home whatever it is called (a `KIRO_HOME` that isn't `.kiro`), and for
  any `.kiro` folder;
- reach those files without naming them. A destructive command (`rm`, `mv`,
  `shred`, `truncate`, a redirect, `find … -delete` or `-exec`, `sed -i`, `rsync
  --delete` and the like) is refused when a **glob**, a **variable**, a **`cd`** or a
  **command substitution** under the kiro home can lead it there. Examples that are
  refused: `rm ~/.kiro/stop*`, `cd ~/.kiro; rm -f stop*`, `d=missions; rm
  ~/.kiro/$d/*.paused`, `find ~/.kiro -name '*.paused' -delete`,
  `rm $(ls -d ~/.kiro/mi*)/*.paused`. The same goes for `bash -c '…'` and `eval`
  of those, and for a Python or Node one-liner that lists the folder and removes
  from it;
- read the app's token log (`/tmp/kiroctl-gui-*`) or call the app's mission API
  (`/api/missions`, `/api/qa-url`). `kiroctl gui --qa-url` is the sanctioned way
  for a QA browser to get into the app;
- run `kiroctl missions pause | resume | end | stop-all | resume-all`, or **0.12.0.** `approve | decline`.
  `kiroctl missions list` is allowed;
- create, change or remove a hook's `.disabled` opt-out;
- **0.12.0.** write an estimate approval: a file named `.kiro-mission*.approval.json`, by any route (a redirect,
  `tee`, `dd`, `install`, `sed -i`, a nested shell, a relative path or a symlink). Reading it is fine. The
  approval is the person's answer to a QA mission's estimate, so an agent can't give it to itself. The same
  holds for the app's approve and decline routes, which answer 403 to an agent's token, and for
  `mission-state.js --clear --estimate-declined`;
- **0.11.0.** run a person-only `mission-state.js` action: `--verify-override` (overriding the completion
  verifier), `--clear --failed` (ending a mission as failed), `--ack-skipped` or `--init --force` (waiving or forcing
  past the preflight), or set `KIROCTL_PERSON_ACTION`. This holds however the command is wrapped (`setsid`,
  `script -c`, `env -i`, a nested shell), because a detached process otherwise looks like a person at a terminal.
  Run these yourself in your own terminal, or use End in the app;
- **0.12.1.** apply a plan amendment (`mission-state.js --apply-amendment`, the app's **Approve amendment**) or
  write an `amended` grill receipt (`grill-receipt.js amend`, alongside `write` and `import`). The chat may
  only `--propose-amendment`. The app's accept and amend routes answer 403 to an agent's token;
- **0.12.3.** write, delete or move a **resolve marker** (`~/.kiro/resolve/`), the file the app writes while a
  [resolve chat](/workflows/missions/#resolve-check-failures) is open. It is protected like the pause files, so
  a chat can't remove it to lift the guard below;
- **0.11.0.** start or advance a mission from any agent other than `dev`, `coder` or `scout`. `mission-state.js --init`, `--set`, `--yield`, `--touch`, the clear command, `--accept-add`, `--accept-set`, `--accept-rm` and `--resume`, `mission-broker.js claim`, `release` and `add-pr`, and `mission-acp-driver.js` are refused. Read-only status still works: `mission-state.js`, `--json`, `--accept-show`, `--accept-json` and `--hours`. `mission-state.js` checks the agent itself, from the chat process. The [global hook](#the-global-hook) refuses the shell commands in a v3 session on a foreign agent.

**The allow-list.** Under the kiro home, a destructive glob, variable or `find` is
allowed only when its first folder is spelled out and is one of `telemetry`,
`skills`, `steering`, `agents`, `prompts`, `cache` or `logs` (the one other case is
below). None of those can hold a pause file. So `rm ~/.kiro/telemetry/repo-cache/*.json` and
`find ~/.kiro/skills -name '*.bak' -delete` work, and `rm ~/.kiro/*`,
`rm ~/.kiro/m*/*` and `rm ~/.kiro/gates/*` don't. A glob in the first position is
refused when it can match `missions`, `stop-all` or `gates`; `rm ~/.kiro/*.json`
can't, so it is allowed. Deleting the kiro home itself is refused. A command
substitution that doesn't mention the kiro home (`rm -rf $(git rev-parse
--show-toplevel)/dist/*`), and any command that leaves the kiro home alone, is
unaffected.

**What it does not chase.** A deliberately obfuscated command gets through:
`base64 … | sh`, an `eval` of a string built at run time, or a script written to
disk and then run. The browser route is the same: an agent that drives the app's
own UI could still click Resume, as the limits in
[Missions](/workflows/missions/#limits-you-should-know-about) say. The refusals
keep an agent from lifting a pause by accident or by an obvious route. They are not
a sandbox.

The gate also no longer trusts a command just because it names a pack script. A
command passes as a sanctioned write only when it actually runs one, as in
`node <pack>/bin/mission-state.js …`. A command such as
`rm .kiro-mission # mission-state.js` used to get through on the name alone. It is
refused now.

## The resolve-chat guard

<Aside type="note" title="0.12.3">
New in 0.12.3. It is part of `mission-state-protect`, and it is always on, with no enable flag.
</Aside>

The app's **Resolve check failures** button opens a `dev` chat to look at a failing Start mission check (see
[Resolve check failures](/workflows/missions/#resolve-check-failures)). That chat could make a red check
green by weakening the check, so the app arms a guard while it is open.

- **The marker.** When the app opens the chat it writes one small file, `~/.kiro/resolve/<project-hash>.json`, naming
  the project folder and the plan. It lives under the kiro home, not in the project, so the chat can't delete it.
  `mission-state-protect` refuses an agent's write, delete or move of that folder, like the pause files.
- **When it ends.** The app removes the marker when the chat's process ends. A marker also stops counting after
  **4 hours**, whether or not it was removed.
- **What the guard refuses** while a marker is live for the project: a write to `qa-contract.json`,
  `qa-contract.local.json`, any `plan*.md` file, the plan the check named, or anything under `.kiro/grill-receipts/`. It
  covers the write tools and shell: a redirect, `tee`, `rm`, `mv`, `sed -i`, `perl -i`, `ruby -i`, a copy or link
  that lands on one of those files, a Python or Node one-liner, `git checkout` and `git restore`. A write through
  a symlink is judged by what the link points at.
- **What it allows.** Reading those files. Copying one somewhere else (only the destination of a copy counts).
  Everything outside those files: the chat can install a missing tool, start the QA test copy, open the sign-in
  terminal and re-run a probe.
- **The way out.** The chat **proposes** the change to the check, and you apply it in the app's person-only
  **Access** section.

The refusal reads `BLOCKED mission-state-protect: a resolve chat must not change the check it is resolving`. As with the
other stop controls, a command that builds the file name at run time is not chased; see
[What it does not chase](#what-mission-state-protect-refuses-even-when-unarmed).

## The CloudCare fence: `cloudcare-fence`

<Aside type="note" title="0.12.3">
New in 0.12.3. The gate is `kiro/gates/cloudcare-fence.js`.
</Aside>

A [`report` mission](/workflows/missions/#the-report-mission-cloudcare) reads client AWS accounts, in production,
on RevStar's admin hub chain (`AdministratorAccess`, then `RevStarSSOAdmin`, then each member's
`OrganizationAccountAccessRole`). RevStar kept that chain and **fences the agent** instead. The fence is a gate on the agent's
tool calls, and it is active only while a mission whose kind is `report` is active for the session.

**What it allows.** Client AWS is reachable through one path:

```text
./cloudcare.sh clients | check | collect | draft | build | render
```

`login` is not on the list. The browser sign-in is a person's step.

**What it refuses.**

- Any other `aws` command, by any spelling: a path, quotes, an `env`, `command`, `xargs` or `sudo` wrapper, an alias, a
  function, `bash -c` or `sh -c`, `eval`, `$(…)`, backticks, a script file or a heredoc.
- `boto3` and `botocore`, `python -c`, inline code in any interpreter, and `pip`. `perl`, `ruby`, `php`, `deno`, `bun` and
  similar are refused outright.
- Anything that names the hub SSO session or profile, a client or hub account id, `assume-role`, `get-role-credentials`,
  `sts`, `~/.aws`, or an `AWS_*` credential variable.
- A `./cloudcare.sh` subcommand outside the six.

**The code lock.** The mission runs CloudCare at the clean commit it started from, recorded at `--init`. Before every
allowed `./cloudcare.sh` call, the gate checks that no tracked file in the repo is modified and that `HEAD` is the recorded
commit. A difference refuses the call. No tool may write inside the repo except under `reports/<client>/<YYYY-MM>/`. A wrong
or missing collector becomes a finding for a person, and the code fix goes through a normal reviewed change on a branch, never under the admin
chain.

**It fails closed.** Every other gate on this page fails open. This one does not: once a report mission is, or may be, active
(the lookup threw, the mission files are ambiguous, or the gate file can't be read), any error blocks the call with
`BLOCKED cloudcare-fence: internal error (…); the fence fails closed`. A broken fence must never look like an open one.

**Always on for a report mission, and no switch.** There is no `.enabled` or `.disabled` file for it. With no report mission
active it allows every call at once and costs nothing. `mission-docs.disabled` does not affect it.

**Limits, stated.** A command whose name or arguments are built by something the parser can't evaluate is refused when
it lands where the command name goes, but an argument assembled at run time that only a program's own logic turns into a
forbidden act (a Makefile recipe, for example) is not chased. The fence is a strong guard against the agent
reaching client AWS by accident or by an obvious route. It is not a sandbox.

## The global hook

<Aside type="note" title="0.11.0">
New in 0.11.0.
</Aside>

The installer writes `~/.kiro/hooks/revstar-workbench.json` from the pack. It is a
global hook file, so it covers agents the pack doesn't own. For any agent that is not
`dev`, `coder` or `scout`, it runs three gates:

| Gate | What it covers there |
| --- | --- |
| `mission-pause` | Pause and stop-all. |
| `mission-state-protect` | Mission state: sentinels, the ledger, receipts and gate flags. |
| `git-protect-gate` | Protected branches. |

The pack's own agents skip it. They run the full set from their agent config. The gates
still respect their enable flags.

**Where kiro-cli reads it.** Measured on kiro-cli 2.37.1: kiro-cli reads this file on
**engine v3** sessions only, and only from `~/.kiro/hooks`. It ignores `KIRO_HOME`
there. A v2 chat does not run it. So the hook is a net for a foreign agent in a v3
session. In a v2 chat, `mission-state.js` does its own agent check (see
[below](#what-mission-state-protect-refuses-even-when-unarmed)).

`kiroctl doctor` has a `global-hook` row. It fails when the file is missing or names a
`global-hook.js` that is missing. The fix is `kiroctl update`. It warns when the file
holds more than the three gates.

The installer and `kiroctl update` also turn kiro-cli Workflows off. See
[Missions](/workflows/missions/#running-a-mission-in-a-dev-chat).

## The stuck-tool watchdog

**0.11.0.** `tool-watchdog` is always on in the `dev`, `coder` and `scout` agents. It ends any tool call that has run for
30 minutes without a result, because a hung command (a prompt waiting for input, a server that never exits, a pipe held open)
otherwise leaves an autonomous mission waiting forever.

- It ends only the process the stuck call started, and that process's children. It never touches the Kiro session itself, MCP
  servers, or anything that was running before the call began.
- The agent sees why in the tool result: the call's output ends with a `[tool-watchdog] ... ended as stuck` line telling it not
  to run the command the same way again. The same notice is shown again on the next turn.
- Sub-agents are covered the same way: a stuck command inside a sub-agent is ended, and the sub-agent and its parent carry on.
- A sub-agent that goes quiet for 30 minutes with no command running is reported as **quiet** (it can't be ended from outside).
  See it with `node <pack>/gates/tool-watchdog.js status`.
- Calls that wait for a person (`user_input`) and the `subagent` call itself are never ended.
- A person can turn it off with `~/.kiro/gates/tool-watchdog.disabled`. Agents can't create that file.

### A chat stuck between tools

**0.11.0.** Sometimes every tool in a turn finishes, but Kiro never hands the results back to the model, so the chat sits
there with nothing running. Ctrl+C and `/compact` don't help. The watchdog also catches this case. When a mission turn has had no
hook event and no tool process for **20 minutes**, it:

- stops the mission's chat loop with the reason **hung**, so the app's Missions drawer and `kiroctl missions` show it as
  stopped (with why) instead of running;
- adds a `[tool-watchdog]` notice that tells you to quit the chat and continue with `kiroctl open --run`, or with
  **Resume mission** in the app;
- ends the chat itself, only for a **pre-approved** mission. Nobody is there to quit it, and nothing is lost: the mission, task
  list and ledger are on disk. A mission you are attending is never ended; you see the notice instead.

A sub-agent that is still working counts as activity, so a long delegation is not mistaken for a hang. **0.11.1.** A long
command that is still running counts too, and when one finishes the 20 minutes start again from that moment. In 0.11.0 a command
that ended right at the 20-minute mark could close a working chat ("Agent connection closed unexpectedly"). The chat is ended
only if its mission still exists and is still pre-approved at that moment, so a chat that has cleared its mission is left alone. Only a v2 mission chat
(`kiro-cli chat --agent-engine v2`) records the chat loop, so a second chat open in the same folder can't make the mission look
dead. `tool-watchdog.disabled` turns this check off too.


**0.11.2: every chat, not only missions.** The same check now covers every `dev`, `coder` and `scout` chat on the v2
engine. Outside a mission, when a chat has had no hook event and nothing running for 20 minutes, the watchdog ends
that chat, because Ctrl+C and `/compact` cannot recover a wedged engine. The conversation is saved, and the next chat
you start in that folder tells you once:

```
[tool-watchdog] your last chat here stopped responding for 25 min and was ended at 14:02. Continue it with `cd '<folder>' && kiro-cli chat --resume-id <id>`.
```

- A tool call that is open with nothing running (for example one waiting for your approval) gets an hour outside a
  mission, not 20 minutes (`KIRO_STALL_OPEN_INTERACTIVE_SEC`).
- A chat waiting for your answer (an open `user_input` call) is never ended.
- `KIRO_STALL_END_INTERACTIVE=0` keeps the check but never ends a non-mission chat (you only get the notice).
- `node <pack>/gates/tool-watchdog.js status` lists recently ended chats with their resume commands.
- Chats on the older v1 engine are not covered yet.
## Mission Control sign-in

RevStar SOP standards and adoption telemetry both run under your **Mission
Control sign-in** (Google, `@revstarconsulting.com`), so every pack agent session
requires it. Sign in once from the RevStar.ai app: `kiroctl gui` → **Sign in with
Mission Control** (the red banner, or Settings → Mission Control). After a
`kiroctl update` on a signed-out machine the app opens for you.

`mc-signin-gate` decides from one small local status file — never the network —
so it is fast and a Mission Control outage never blocks you. It refuses a prompt
only when:

- you are **not signed in**, or
- Mission Control **definitively rejected** your saved sign-in (expired or
  revoked).

It allows the prompt when you are signed in, when a bypass is active, when
Mission Control's kill switch is on, when the status is unknown or unreadable,
when RevStar.ai's CLI can't be found, and on any internal error. A **running
mission** that started while you were signed in keeps running (it gets a note
instead of a block); new sessions are blocked after it clears.

No browser on this machine, or Mission Control down? Use a time-limited, logged
bypass (1–72 hours), reported to Mission Control:

```sh
kiroctl sop bypass --hours 4 --reason mc-outage    # mc-outage | no-browser | other
kiroctl sop bypass --clear
```

The gate only runs in the pack's agents (`dev`, `coder`, `scout`).

## The QA fan-out gate

Not a hook: a check built into `mission-state.js --clear` itself, so it runs **on every
machine without being armed** (like telemetry and the sign-in, a deliberate exception to
"inert until armed"). On a mission's clean clear it re-works-out everything the mission's
changes reach, and **refuses the clear** unless:

- QA ran at all, if the changes reach any page, endpoint or job;
- every target was tested and passed **since its code last changed** — editing code on a
  target's chain after testing it means re-testing it;
- every waived target names a tested stand-in of the same kind that reaches the same
  changed code;
- every changed item has a tested target of each kind it reaches, and at least the
  minimum sample was tested.

"The mission's changes" means each repo's diff against the base branch frozen at
`--init` (see [which branch it measures against](/workflows/qa-and-design/#scoped-runs-the-change-and-everything-connected-to-it)),
the same diff a pull request shows. Missions started before 0.8.4 work the branch out on each run.

The refusal lists what's missing and the exact commands to fix it. A change that reaches
nothing (docs, tests) needs no QA. Missions that started before the update are exempt. If
the check itself can't run (no git, or it takes over 2 minutes), it **fails open**: the
mission clears with a note, and the app's Mission Control panel shows how often that
happened in the last 7 days.

**Which repos it checks.** The repos come from the mission's entry in the mission index
(`~/.kiro/missions/`). Each time a gate resolves a session to the mission from inside a
repo or a git worktree, that path is added to the entry (the worktree's path, not the main
checkout, because the work is on the worktree's branch), and the project's known repos are
added for any not yet seen. Only then does it fall back to the mission root's
`.kiro/repos.json` and `git`. From 0.9.0 an empty list no longer fails open. The clear is
refused:

```text
fan-out gate: REFUSED — no repositories found for this mission; name them with `--repos <paths>`, or pass `--no-repos` if no code changed
```

Name the repos with `mission-state.js --clear --repos <path> [<path> …]`, or pass
`--no-repos` when the mission changed no code. The choice is recorded on the exit receipt.
The 2-minute timeout and a git failure still fail open.

**Off-switch (a person only):** create `qa-fanout-gate.disabled` in `~/.kiro/gates/` (or
the project's `.kiro/gates/`) **before** starting the mission. A flag created during a
mission is ignored, and agents can't create it.

## The delivery docs check

<Aside type="note" title="0.12.2">
New in 0.12.2.
</Aside>

Not a hook either: a step in `mission-state.js --clear`, after the fan-out gate and, for a full QA mission, the
full-run receipt. It applies only to a mission whose delivery docs are on, a value frozen when the mission
started (see [Delivery docs](/workflows/missions/#delivery-docs)). It reads that frozen value and never the
mission's kind. A mission with no such value, such as one that began before 0.12.2, is not checked.

It refuses the clear unless:

- the UAT guide exists and is newer than the newest QA capture, when the mission has a capture with a `pass` or
  `fail` result;
- the blockers page exists and is newer than the newest deferral change, when the mission has a deferral someone
  outside it must act on;
- every such deferral has non-empty `resolutionSteps`.

The refusal names each missing item and the command that makes it. It only looks that the files exist. It
doesn't read them again, and **videos are never required**. If the check itself fails to run, it **fails open**:
the mission clears with a `delivery docs gate: FAILED OPEN` note, and the failure is logged to
`delivery-docs-failopen.jsonl`.

**Off-switch (a person only):** create `mission-docs.disabled` in `~/.kiro/gates/` (or the project's
`.kiro/gates/`) **before** starting the mission. A flag created during a mission is ignored, and agents can't
create it. The docs are on by default, so there is no `.enabled` file.

## Verifying gates

Run the full self-test suite, which asserts every gate in both directions
(should-fire and should-not-fire):

```sh
node kiro/gates/selftest.js
```

A clean run reports every case passed (354/354 on 0.10.0). **0.11.0.** A should-fire (RED) case
passes only when the gate exits `2` **and** its stderr carries that gate's own refusal text
(for example `BLOCKED mission-state-protect`). A gate that exits `1` with no message, or refuses
for some other reason, fails the case: Kiro blocks on any non-zero exit, so a crashing gate would
otherwise look like a working one. The installers run the selftest in its fast mode
(`KIRO_SELFTEST_FAST=1`), which includes the gate sections of the `mission-pause` suite
(`node kiro/bin/test-mission-pause.js --quick`: pause and stop-all refusals, the `goal` tool
passing through, resume). Scope the selftest to one gate or get verbose output:

```sh
node kiro/gates/selftest.js qa
node kiro/gates/selftest.js --verbose
```

To see the real payload a gate receives when it doesn't fire as expected:

```sh
KIRO_GATES_DEBUG=1 node kiro/gates/<gate>.js < /dev/null
```
