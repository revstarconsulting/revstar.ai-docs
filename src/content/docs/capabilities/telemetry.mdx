The `telemetry-emit` gate reports RevStar.ai adoption to Mission Control
(receiver: ADO #144788). It is an **always-on hook**: mandatory RevStar policy,
**not arm-gated** — a deliberate, documented exception to "inert until armed". It
never blocks a tool call and fails open.

Telemetry runs under your **Mission Control sign-in** — the same Google sign-in
that powers RevStar SOP standards. See [Gates → Mission Control sign-in](/capabilities/gates/#mission-control-sign-in).

## What it sends

Eight event types, nothing else:

| Event | Meaning |
| --- | --- |
| `mission_started` | A mission was set (once per mission — re-running `--init` does not re-send it). Carries `estimated_conventional_hours` when the plan's estimate has a `conventional:` value. |
| `mission_cleared` | A mission was cleared from its completion audit (once). `hours_autonomous` is measured from the run's active time; `actual_hours` is sent only when you give it at clear time. A bare clear from any other state is reported as `mission_failed` (abandoned). |
| `mission_failed` | A mission ended without clearing (once). |
| `skill_run` | A skill was invoked. |
| `qa_result` | A full QA run produced a result, with `bugs_found` (cases failing this run) and `bugs_fixed` (cases that failed earlier in the mission and pass now). |
| `preflight` | A preflight check ran. |
| `mc_gate_bypass` | You used the time-limited sign-in bypass (`kiroctl sop bypass`): hours + a reason from `mc-outage \| no-browser \| other`. |
| `client_heartbeat` | RevStar.ai is installed, signed in and in use on this machine, so you appear in Mission Control even on a day with no other events. Sent at most **once per machine per day** (sent from 0.6.8; 0.6.5–0.6.7 recorded it but held it locally), from the first of: a `dev`/`coder`/`scout` session starting (`trigger: session`), the app opening (`app`), or an install / `kiroctl update` (`install`). Carries the channel, platform, Kiro version, and two yes/no flags: the pack is current and the default agent is a RevStar.ai agent. No paths, repo names or project. |

## When it sends

Each event is written to a local durable spool the instant it happens, so
telemetry never blocks you. A separate detached, throttled flusher then sends
batches opportunistically — on hook and skill activity, and at session start.

Events can lag slightly, but they always roll up to the correct day: the server
dates each event by its `occurred_at` and de-duplicates by `event_id`. Late,
offline, batched, and retried sends are therefore safe. Events waiting on Mission
Control (not signed in yet, or the ingest key not available) are **kept** — the
spool is only capped as a disk guard (100,000 events, months at real volumes);
`doctor` warns well before that.

## Identity and sign-in

Events are sent with a **per-developer ingest key** that Mission Control issues
off your sign-in: RevStar.ai presents your Mission Control sign-in once, receives a
key scoped to telemetry ingest only, keeps it in your OS keychain, and sends it as
`Authorization: RevStarIngest <key>` to Mission Control's dedicated token route
(`…/v1/ingest/revstar-ai/token`). It survives offline and late sends, and Mission
Control can revoke it without signing you out. If ingest says the key is unknown
or revoked, RevStar.ai requests a new one once; if that fails, events are kept and
`doctor` / the app say what to do (sign in again, or ask Mission Control to activate
your account). Your sign-in token itself is never sent to ingest. While a machine
can't get a key and already has the legacy shared key, it keeps sending with that
meanwhile, so the transition never drops telemetry.

Events are reported under the `@revstarconsulting.com` email of your Mission
Control (Google Workspace) sign-in, and Mission Control binds the email to the key
server-side.

<Aside type="note">
**Rollout:** Mission Control's key service is being built. Until it is switched
on, machines that already have the legacy shared ingest key keep sending with it,
and everyone else's events are kept locally and send automatically once it is on
— nothing is lost.
</Aside>

Not signed in yet? Events are **held** locally — attributed to no one, never
lost — and sent under your email the first time you sign in. Sign in from the
RevStar.ai app (`kiroctl gui` → **Sign in with Mission Control**).

A client project's SSO never changes who you are: the client only determines which
project the work counts toward (`mc_project_id`).

## Privacy

- **Email is the only PII.**
- **No free-form content is ever sent** — no prompt text, source code, file
  contents, or customer data. The one project identifier sent is the repository's
  git origin as `owner/name` (e.g. `acme/web-app`), so Mission Control can
  attribute work to the right project.
- Events are strictly validated against an allowlist: unknown top-level fields
  are rejected, and enumerated fields use bounded values.

## Project attribution (`repo` + `mc_project_id`)

Every event carries `repo` (the git origin as `owner/name`), and `mc_project_id`
when the project is pinned. Mission Control uses the pin first, then matches the
repo, then falls back to "All-RevStar".

To pin the project, after you sign in RevStar.ai looks up your Mission Control
projects:

- **exactly one** of your projects matches the repo → it is pinned automatically;
- **several** match, or the repo belongs to a project you're not on → the RevStar.ai
  app asks once, *"Which Mission Control project is this repo for?"*, in a banner
  and under Settings → Mission Control;
- **none** match → events omit `mc_project_id` and carry the repo only;
- you're on **one** project and Mission Control won't say which project owns the
  repo (most developers) → that project is pinned, as the best available guess.

The pin is saved per folder in `.kiro/telemetry-project.json` (committable, so a
team answers once), in the folder where your Kiro sessions start: the project's
repo when it has one, otherwise the project folder.

**Automatic pins are re-checked once a day.** If Mission Control later adds you
to the repo's real project, the pin moves, or the app asks you to pick. Pins you
chose yourself are never changed.

**Wrong project?** Run [Diagnostics](#diagnostics-report) and look at **Project
attribution**. For each project and repo it shows which Mission Control project
the events go to, why (picked by you, or automatic), whether that matches the
repo in Mission Control, and what was recently reported. To fix a pin:

- `kiroctl telemetry project --reset --dir <repo folder>` drops it and looks it up
  again (the app asks if several projects fit);
- `kiroctl telemetry project --set <id> --dir <repo folder>` pins one by hand.

If your real project isn't in the **your projects** list, Mission Control doesn't
have you on it yet. Ask the Mission Control team to add you first, otherwise
RevStar.ai can't attribute work to it.


## Self-check and repair

At the start of every `dev` session the `mc-session-health` hook checks the
Mission Control connection in milliseconds (local files only) and launches a
**detached** repair in the background — refresh the sign-in, get the ingest key, resolve the
project, send held events, flush. Session start never waits on Mission Control.
It only adds a note to the session when something that needs you **changes**.

The same health model shows in `kiroctl doctor` (the `mc …` rows), in
`kiroctl telemetry status`, and in the app under Settings → Mission Control
(with a **Check now** button). Each row is *Working*, *Note* (expected — e.g.
"queued — waiting on Mission Control"), *Retrying*, or *Needs you* with
the one thing to do.

### Download errors

Settings → Mission Control → **Download errors** saves a text file to your
Downloads folder with what Mission Control rejected (`telemetry/rejected.log`),
the last send, the last background check and the current health rows. It's
redacted the same way as the diagnostics report. Send it to the maintainer when
the **Rejected events** row appears.

### Diagnostics report

For anything those rows don't explain, run the full self-diagnostic: in the app,
**Settings → Diagnostics → Run diagnostics** (or `kiroctl diagnose` in a terminal).
It checks:

- **System:** OS, Node, `kiroctl` version and channel, `kiro-cli` version, and whether you're logged in to Kiro.
- **Installation:** the install record and both folders, whether GitHub is reachable for updates, every hook script the `dev`/`coder`/`scout` agents reference, the sign-in gate and telemetry hook wiring, the default agent, any shadowing agent-name conflict, and steering.
- **Skills:** every installed skill is readable and matches the pack.
- **Connections:** the Mission Control self-repair (sign-in refresh, ingest key, project, send).
- **Mission Control & telemetry:** sign-in, endpoint, how many skill uses were ever recorded, what's queued, the last send, the last heartbeat.
- **Project attribution:** your Mission Control projects, the project each of your app projects and repos reports to and why, whether it matches the repo, and the recently reported repo → project pairs.
- **Doctor:** every `kiroctl doctor` row.
- **Live Kiro session test** (optional, about 15 seconds each): runs a real `dev` session that reads a skill, then confirms the skill use was recorded. It runs in your normal home if Kiro is logged in there, and in the first client you're signed in to, from one of that client's projects (the setup you actually work in). It also catches Kiro refusing the read (`workspace-escape`). Kiro logins are kept per client, so "not logged in outside client projects" is normal.

Problems are listed first. **Copy report** or **Download report** gives you text
to send to the RevStar.ai maintainer. The report includes your email, versions,
paths (home shown as `~`) and statuses. It never reads token or key files, and
anything token-shaped is removed.

## Always on, mandatory

Telemetry is mandatory RevStar policy. There is no in-software opt-out, consent
prompt, or disclosure UI. Consent and disclosure live in the employment
agreement — a policy/HR layer — and are deliberately not duplicated in the
software.

## Kill switch

The off-switch is **server-side**, held by Mission Control — not a local toggle.
If MC disables RevStar.ai telemetry, the ingest returns a terminal
`403 {"disabled": true}`; the emitter then **drops its queued events** (it does
not spool or replay them) and backs off before trying again. While the kill
switch is on, the Mission Control sign-in gate is also off.

## Environment

Mission Control fans every event out to all environments and resolves each on
its side, so `environment` is **advisory** — the emitter does not set or manage
it. (If a value is ever supplied it must be `"sandbox"` or `"prod"`.)

## Commands

| Command | What it does |
| --- | --- |
| `kiroctl telemetry status` | Identity, queue depth, last flush, and the connection health rows. |
| `kiroctl diagnose [--no-live] [--json] [--out <file>]` | The full diagnostics report (same as Settings → Diagnostics). Exits non-zero if anything fails. |
| `kiroctl telemetry repair [--dir <p>]` | Run the self-repair now (refresh, project lookup, flush). |
| `kiroctl telemetry flush` | Flush the spool manually. |
| `kiroctl telemetry config [--endpoint <u>] [--mint-url <u>\|off] [--auth minted\|shared-key]` | View or set the ingest endpoint and the ingest-key settings. |
| `kiroctl telemetry project [--set <id> \| --reset] [--dir <p>]` | Show, pin by hand, or drop and re-resolve the Mission Control project for a folder. |
