---
title: Skills
description: The 29 on-demand playbooks RevStar.ai installs, grouped by purpose.
---

A skill is a playbook that loads **on demand** — its metadata is available at
startup, but its full body only loads into context when your request matches
its trigger. You don't invoke skills directly; the active agent picks the one
that fits, most often `dev`.

## Engineering

| Skill | When it fires |
| --- | --- |
| `context` | Start of a fresh implementation task — gather context, resolve unknowns, plan, then build. |
| `code` | Writing or implementing code — functions, features, endpoints, modules. |
| `debug` | A bug, error, failing test, or unexpected behavior needs root-cause analysis. |
| `refactor` | Restructuring without changing behavior — "clean this up", "extract", "rename". |
| `review` | Pre-PR review focused on security, correctness, and performance. |
| `architecture` | System design decisions — structure, boundaries, data flow, technology choices. |
| `standards` | Enforcing or evolving team coding conventions. |

## Delivery & comms

| Skill | When it fires |
| --- | --- |
| `breakdown` | PM-friendly task breakdown of code changes, specs, or completed work. |
| `changelog` | Release notes and changelogs from diffs or commit history. |
| `status` | Client-facing status updates from vault state and recent work. |
| `handoff` | Session context summary for handing work off to a sibling project/repo. |
| `submit` | The pre-PR pipeline — secret scan, gates, review, then commit/push/PR. Commits in logical, reviewable units (never one giant commit) and fills the project's PR/MR template when it has one, instead of a freeform description. Never auto-merges outside a mission; **0.11.0.** in a mission the phase audit is the review. |

## Autonomy, QA & design

| Skill | When it fires |
| --- | --- |
| `mission` | Setting, updating, or clearing the standing macro-goal for multi-phase work. **0.11.0.** Also the `/mission` slash command, for a multi-phase goal that no other shortcut fits. |
| `qa` | Running the QA protocol against staging. Scoped by default — the change plus every connected page, endpoint and job, across the project's repos; full only when you ask for it or the grilled plan declares it (`## QA Scope`); or "today". |
| `design` | Building or restyling any UI surface — builds to the project's **design authority** (the plan's pinned `## Design Authority`: a customer mockup, or the committed brand guide) and enforces the full component state set, instead of inventing a second design language. |
| `brand-guide` | Captures a web app's existing design language into a committed, reviewed `.kiro/context/brand-guide.md` (tokens + component catalogue w/ states + layout + icon/motion + screenshots + known inconsistencies), generated from the codebase design system crossed with the rendered app. The design source-of-truth the `design` skill builds to and `qa` enforces. First run on a UI project prompts to generate it; re-run on a redesign. |
| `grill-me` | Adversarial interrogation of a plan or design until every gap is resolved. Forces the plan into **phases → features** and grills **two dimensions, both deep** — the cohesive whole and **every** feature — so a big plan gets the same rigor per decision as a single feature; keeps an advisory **Grill Coverage** checklist (grilled / deferred / still-open) and asks every question in plain English. On an ADO-tracked project, an unanswered question becomes a tracked request — a comment on the related item, or a new "Information request: …" item — assigned to the project's PM. Also decides the QA scope: it checks five triggers itself and, if any applies, recommends a full regression, and writes your decision into `## QA Scope`. It also writes the plan's `## Required Access` block: one probe per external dependency, and the grill receipt isn't written until each is verified, deferred to kickoff with a reason, or descoped (see [Missions → Access](/workflows/missions/#access-you-must-declare-it)). **0.12.1.** When an answer narrows or reverses an earlier decision it **replaces** the earlier sentence (a "superseded by …" note stays in the decision log only), runs a consistency pass for sentences that cannot both be true, and the receipt writer refuses a plan whose [contradiction check](/workflows/missions/#the-contradiction-check) finds a pair. |
| `pm-grill-me` | The **non-developer** counterpart to `grill-me`: the same relentless, one-at-a-time interrogation and multi-pass gap audit, but for product owners / PMs. It interrogates only **product and business** branching (scope, users, journeys, prioritisation, value) and is **banned from any technical or implementation questions** — anything an engineer would own is left for the developer `grill-me`. Also asks, in product terms, whether to re-test everything before release, and writes the answer into `## QA Scope`. It also asks, in product words, where each outside connection lives and whether it can be checked from here, and the receipt waits for the plan's access to be accounted for. |
| `estimation` | Estimating a grilled plan as an autonomous mission — build wall-clock **plus** human-oversight hours — or a quick scope/risk read when there's no plan file. AI/LLM workloads are flagged and estimated separately. Every plan estimate ends with a required `kiro-estimate` block that makes its assumptions explicit, is self-gated by an estimate-receipt, is reconciled across sessions, and feeds a memory-backed self-calibration loop. A plan-declared full QA run is its own line, counted per run and per app. |
| `build-plan` | The daily "implement every phase of the plan" slash command — runs the whole plan as a pre-approved mission (audit + scoped `qa` per phase, then scoped QA over the whole mission's diff, a requirement-by-requirement audit, and a clear — full QA only when you ask for it or the plan declares it). Replaces the long paste-in prompt. Invoke in a v2 `dev` chat: `/build-plan [plan=<path>] [branch=<branch>]` — `plan=` defaults to `plan.md`; `branch=` optional (defaults to `staging`, then the remote default, then `main`; a named branch that doesn't exist stops the run). |
| `fix-bugs` | The "reproduce, fix and QA-verify every reported bug" slash command — treats every item in a bug report as an active bug, reproduces each in Playwright, fixes at the owning layer, re-verifies, then audits and clears. Invoke: `/fix-bugs [doc=<path>] [ado=123,456] [branch=<branch>]` — give a bug document, **0.12.0.** ADO work item ids, or both (at least one). `ado=` takes any work item type, and a Closed or Removed id stops the run before it starts. With ADO ids the skill writes the items into `qa-reports/fix-bugs-<mission-id>.md` and uses that file as the bug document. It files an ADO Bug for each bug in a `doc=` document (no duplicates, tagged `kiro-mission` and `kiro-mission:<mission-id>`). It lands the fixes through one PR, and moves an item to the project's **done state** only after the fix is live on staging. `branch=` as above. See [Azure DevOps](/workflows/azure-devops/#missions-and-ado). |
| `qa-mission` | **0.12.0.** The QA slash command that runs as an enforced, pre-approved mission. It always starts with a **full `qa` audit**, then does one of three things, chosen by `variant=`: `full` stops there and delivers the report and coverage receipt; `fix` triages every finding, fixes the defects, lands them through a PR and re-tests; `regression` turns the test registry into a scripted regression suite (Playwright for web, Mobilewright on Mobile Next for mobile). Invoke: `/qa-mission variant=full\|fix\|regression [branch=<name>] [estimate-first=yes] [mobile-minutes=<n>]`. For `regression` add `repo=<existing>` **or** `new-repo=<org>/<name>`, and optionally `ci=yes\|no`, `ci-system=<system>`, `web-runs=pr\|nightly\|manual`, `mobile-runs=pr\|nightly\|manual`, `mobile=yes\|no` and `secrets=NAME:from,...`. It asks, and does not guess, when `variant` or the regression target is missing. See [QA missions](/workflows/qa-and-design/#qa-missions). |
| `ci-qa-coverage` | **Deprecated.** Now a one-release alias for `/qa-mission variant=regression`. It tells you so, passes `branch=` on and starts that skill, which asks for the repo. **The alias is removed in 0.13.0.** Before 0.12.0 it ran a full audit and wrote only the catalog `qa-reports/ci-regression-candidates.md`. The regression variant still writes that file, then writes the tests too. |

The app's **Start mission** drawer launches these missions for you: it builds the slash line, checks the project is ready, and opens a terminal with a v2 `dev` chat whose first message is that line. **0.12.0.** It replaces the **Shortcuts** drawer, and your saved variations are now **presets** on the matching mission type. See [Starting a mission from the app](/workflows/missions/#starting-a-mission-from-the-app). **0.11.0.** The slash lines no longer start with `/goal`.

## Azure DevOps, KB & authoring

| Skill | When it fires |
| --- | --- |
| `ado-telemetry` | Read-only Azure DevOps pulls — sprint status, work items, roadmap. |
| `ado-write` | Creating or updating Azure DevOps work items to exact conventions. Also drives the enforced item lifecycle — `Active` (or the client's start state, 0.11.0 beta) + assigned at start; at done, moves the item to the ready-for-QA/UAT state, assigns it, and comments — and records a receipt (checked by `ado-receipt-gate`). |
| `kb` | Regenerating the project's living knowledge base — architecture, ERD, API, infra docs. |
| `project-map` | Auditing an unfamiliar or freshly-linked repo into a concise `.kiro/context/architecture.md` navigation map, so sessions orient fast. Manual, per-project. |
| `project-context` | Maintaining the committed `.kiro/context/` bundle (architecture, gotchas, decisions) so a different developer can pick the project up from a clone. Auto-loads via a committed steering pointer; refreshed at the end of a mission. |
| `skill-creator` | Authoring a new skill — interviews you and drafts a well-formed `SKILL.md`. |

## Registering a custom skill

```sh
kiroctl onboard --kind skill --name <name> --source <path>
```

This is governance-gated — `kiroctl doctor --governance` checks that a
registered skill is well-formed before it's trusted alongside the built-in 29.
