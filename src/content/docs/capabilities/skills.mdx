---
title: Skills
description: The 22 on-demand playbooks RevStar.ai installs, grouped by purpose.
---

A skill is a playbook that loads **on demand** — its metadata is available at
startup, but its full body only loads into context when your request matches
its trigger. You don't invoke skills directly; the active agent picks the one
that fits, most often `dev`.

## Engineering

| Skill | When it fires |
| --- | --- |
| `context` | Start of a fresh implementation task — gather context, resolve unknowns, plan, then build. |
| `code` | Writing or implementing code — functions, features, endpoints, modules. |
| `debug` | A bug, error, failing test, or unexpected behavior needs root-cause analysis. |
| `refactor` | Restructuring without changing behavior — "clean this up", "extract", "rename". |
| `review` | Pre-PR review focused on security, correctness, and performance. |
| `architecture` | System design decisions — structure, boundaries, data flow, technology choices. |
| `standards` | Enforcing or evolving team coding conventions. |

## Delivery & comms

| Skill | When it fires |
| --- | --- |
| `breakdown` | PM-friendly task breakdown of code changes, specs, or completed work. |
| `changelog` | Release notes and changelogs from diffs or commit history. |
| `status` | Client-facing status updates from vault state and recent work. |
| `handoff` | Session context summary for handing work off to a sibling project/repo. |
| `submit` | The pre-PR pipeline — secret scan, gates, review, then commit/push/PR. Commits in logical, reviewable units (never one giant commit) and fills the project's PR/MR template when it has one, instead of a freeform description. |

## Autonomy, QA & design

| Skill | When it fires |
| --- | --- |
| `mission` | Setting, updating, or clearing the standing macro-goal for multi-phase work. |
| `qa` | Running the QA protocol against staging — scoped, full, or "today". |
| `design` | Building or restyling any UI surface — builds to the project's **design authority** (the plan's pinned `## Design Authority`: a customer mockup, or the committed brand guide) and enforces the full component state set, instead of inventing a second design language. |
| `brand-guide` | Captures a web app's existing design language into a committed, reviewed `.kiro/context/brand-guide.md` (tokens + component catalogue w/ states + layout + icon/motion + screenshots + known inconsistencies), generated from the codebase design system crossed with the rendered app. The design source-of-truth the `design` skill builds to and `qa` enforces. First run on a UI project prompts to generate it; re-run on a redesign. |
| `grill-me` | Adversarial interrogation of a plan or design until every gap is resolved. Forces the plan into **phases → features** and grills **two dimensions, both deep** — the cohesive whole and **every** feature — so a big plan gets the same rigor per decision as a single feature; keeps an advisory **Grill Coverage** checklist (grilled / deferred / still-open) and asks every question in plain English. On an ADO-tracked project, an unanswered question becomes a tracked request — a comment on the related item, or a new "Information request: …" item — assigned to the project's PM. |
| `pm-grill-me` | The **non-developer** counterpart to `grill-me`: the same relentless, one-at-a-time interrogation and multi-pass gap audit, but for product owners / PMs. It interrogates only **product and business** branching (scope, users, journeys, prioritisation, value) and is **banned from any technical or implementation questions** — anything an engineer would own is left for the developer `grill-me`. |
| `estimation` | Estimating a grilled plan as an autonomous mission — build wall-clock **plus** human-oversight hours — or a quick scope/risk read when there's no plan file. AI/LLM workloads are flagged and estimated separately. Every plan estimate ends with a required `kiro-estimate` block that makes its assumptions explicit, is self-gated by an estimate-receipt, is reconciled across sessions, and feeds a memory-backed self-calibration loop. |
| `build-plan` | The daily "implement every phase of the plan" `/goal` shortcut — runs the whole plan as a pre-approved mission (audit + `qa` per phase, then full QA, a requirement-by-requirement audit, and a clear). Replaces the long paste-in prompt. Invoke: `/goal Run the build-plan skill branch=<branch> --max 50` — `branch=` optional (defaults to `staging`, then the remote default, then `main`; a named branch that doesn't exist stops the run). |
| `fix-bugs` | The "reproduce, fix and QA-verify every reported bug" `/goal` shortcut — treats every item in a bug report as an active bug, reproduces each in Playwright, fixes at the owning layer, re-verifies, then audits and clears. Invoke: `/goal Run the fix-bugs skill doc=<path> branch=<branch> --max 50` — `doc=` is the bug-report path(s); `branch=` as above. |
| `ci-qa-coverage` | The "explore + full QA + find the CI/CD test gaps" `/goal` shortcut — explores the repos you can reach and the linked ADO project, runs a **full `qa` audit**, inventories existing automated coverage, then catalogs every QA-exercised behavior not yet covered as **CI/CD regression candidates** (`qa-reports/ci-regression-candidates.md`). It produces the catalog the automation repo consumes; it does **not** write the tests (that's the follow-up). Invoke: `/goal Run the ci-qa-coverage skill branch=<branch> --max 50`. |

The project GUI's **Shortcuts** panel exposes these `/goal` shortcuts as one-click prompts, and also ships two free-form quick prompts that wrap the `qa` skill directly: **"QA full"** (`/goal run /qa full`) and **"QA full + fix issues"** (`/goal run /qa full` then the `fix-bugs` skill). All are capped at `--max 50`, and you can save per-project variations alongside them.

## Azure DevOps, KB & authoring

| Skill | When it fires |
| --- | --- |
| `ado-telemetry` | Read-only Azure DevOps pulls — sprint status, work items, roadmap. |
| `ado-write` | Creating or updating Azure DevOps work items to exact conventions. Also drives the enforced item lifecycle — `Active` + assigned at start; at done, moves the item to the ready-for-QA/UAT state, assigns it, and comments — and records a receipt (checked by `ado-receipt-gate`). |
| `kb` | Regenerating the project's living knowledge base — architecture, ERD, API, infra docs. |
| `project-map` | Auditing an unfamiliar or freshly-linked repo into a concise `.kiro/context/architecture.md` navigation map, so sessions orient fast. Manual, per-project. |
| `project-context` | Maintaining the committed `.kiro/context/` bundle (architecture, gotchas, decisions) so a different developer can pick the project up from a clone. Auto-loads via a committed steering pointer; refreshed at the end of a mission. |
| `skill-creator` | Authoring a new skill — interviews you and drafts a well-formed `SKILL.md`. |

## Registering a custom skill

```sh
kiroctl onboard --kind skill --name <name> --source <path>
```

This is governance-gated — `kiroctl doctor --governance` checks that a
registered skill is well-formed before it's trusted alongside the built-in 21.
