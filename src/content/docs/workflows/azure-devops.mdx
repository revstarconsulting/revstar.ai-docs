## It's a skill, not a router agent

ADO integration is delivered as the **`ado-write`** skill — not a dedicated
routing agent. Any agent that has the skill available can post an update; you
don't need to switch context to a separate ADO-only assistant.

The **`azure-devops`** MCP server is wired up automatically at install. Its
tools are invoked through the `ado-write` skill, which knows RevStar's exact
conventions for how a ticket should be written — the MCP server itself is just
transport.

## Writing conventions

`ado-write` enforces the house format so tickets are consistent across the
team:

- **Hour fields are always `0`.** Time is owned by the PM in ADO. Effort is
  reported **narratively** in the summary text, never as a structured hours
  value.
- **Exact daily task title:** `<Role> - <Full Name> - <MMDDYYYY>`, where `Role`
  is `Dev`, `DevOps`, or `AI`.
- **Field name is `Custom.TeamCode`** — not `RSCode`.
- **Summary format** follows four sections: Summary, Changes, Notes, Testing.

<Aside type="tip">
Reporting progress to your daily task is **standard practice**, not something
you opt into — as work happens, post the update. The standard
[work-item lifecycle](#the-enforced-work-item-lifecycle) on the item your branch
is bound to is **pre-approved** — no per-change confirmation. Only genuinely
non-standard edits (someone else's item, deletes, odd state jumps, items not
bound to the branch) are gated behind explicit confirmation.
</Aside>

## The enforced work-item lifecycle

For ADO-tracked work, `ado-write` drives the item the branch is bound to
through a fixed lifecycle:

1. **At start** — the item moves to `Active` and is assigned to the developer.
   **0.11.0.** If the client has a [Start state](#set-up-ado-for-a-client-org-project-pat), the item
   moves to that state instead, walking the client's state path in order when the board requires it.
2. **At done, before opening the PR** — the item moves to the project's
   ready-for-QA/UAT state (the client's **Done state**), is assigned to the
   **Done assignee**, and gets a comment describing what was done. Hours stay
   `0`, per the writing conventions above.

Each update is recorded as a **receipt**. The **`ado-receipt-gate`** turns the
lifecycle from a convention into a rule: when armed, it blocks opening a PR
(`gh pr create`, `glab mr create`, `az repos pr create`) from a
`feat/<id>-*` branch until the item's status / assignee / comment update has
been recorded.

```sh
touch ~/.kiro/gates/ado-receipt-gate.enabled
```

It is **disarmed by default** and **fails open** — any uncertainty or error
allows the PR — and it only fires for ADO-bound `feat/<id>-*` branches. Work on
any other branch is untouched. **0.11.0.** The app's Settings → Gates has a checkbox that arms
and disarms it. See [Gates](/capabilities/gates/#the-ado-receipt-gate-in-the-app).

## Set up ADO for a client (org, project, PAT)

ADO is configured **per client** and injected automatically when you
`kiroctl open` a project bound to that client — no manual `export`. Set these
on the client, once:

- **Org URL + default project** — in the GUI, from the selected project's
  **Azure DevOps** card (**Edit**) — the org URL and project fields there — or
  from the CLI:

  ```sh
  kiroctl client set-ado --slug <client> \
    --ado-org https://dev.azure.com/YourOrg --ado-project "Your Project"
  ```

- **Project manager (PM)** — who ADO **information requests** get assigned to (the
  `grill-me` skill files one when a question can't be answered). Set it in the same
  **Azure DevOps** card's **PM** field: where the PAT allows it, that's a **typeahead
  pulled from your ADO project's members** (type to fuzzy-match); otherwise it's a
  free-text box you type the name into. Or from the CLI:

  ```sh
  kiroctl client set-ado --slug <client> --ado-pm "Jordan Lee"
  ```

- **Start state** — **0.11.0.** The board state the item moves to when work starts. Optional. If
  it is unset, nothing is injected and `ado-write` uses `Active`. Set it in the **Azure DevOps** card, or:

  ```sh
  kiroctl client set-ado --slug <client> --start-state "Development"
  ```

  If the board only lets an item move one step at a time, add the **state path**: the states in order,
  separated by commas. `ado-write` walks it from the first state to the start state.

  ```sh
  kiroctl client set-ado --slug <client> --start-state "Development" \
    --state-path "New,Ready to Build,Development,QA"
  ```

  Rules: the start state must appear in the path when a path is given; a path needs a start state; each
  state is at most 64 characters; at most 20 states; no commas inside a state and no duplicates. Pass
  `""` to clear either value. `kiroctl client list` shows them as `start=X path=A>B>C`, and the app's ADO
  edit form has both fields.

- **Done state** — the board column/state that means *ready for QA/UAT*; the
  lifecycle moves the item here when work is done. If it's unset or non-standard,
  the agent asks once and saves the answer. Set it in the **Azure DevOps** card, or:

  ```sh
  kiroctl client set-ado --slug <client> --done-state "Ready for QA"
  ```

- **Done assignee** — who the item is assigned to at done. Defaults to the project
  PM when blank; set a per-project override in the same card, or:

  ```sh
  kiroctl client set-ado --slug <client> --done-assignee "Jordan Lee"
  ```

- **PAT** (scoped per client, never global) — from the same card, or piped in
  from the CLI (never passed as an argument):

  ```sh
  printf '%s' '<pat>' | kiroctl client set-pat --slug <client>
  ```

The PAT is stored in the OS keychain (falling back to a `0600`-permission file)
and is **never** written into `mcp.json`. It (and the org/project) are injected when
you **`open`** the project — so set the PAT *before* opening, and if you change it,
**relaunch** the session for the new value to take effect (a running session keeps
what it launched with).

### What `open` injects

When you open a project bound to the client, `kiroctl open` injects the client's
ADO config into the session in **both** naming conventions, so both consumers
work with zero manual setup:

- `AZURE_DEVOPS_PAT` / `AZURE_DEVOPS_ORG_URL` / `AZURE_DEVOPS_DEFAULT_PROJECT` —
  for the **`azure-devops` MCP server** (the `ado-write` / `ado-telemetry` skills).
- `ADO_PAT` / `ADO_ORG_URL` / `ADO_PROJECT` (+ `ADO_PM` when a PM is set) — for the
  **`kiroctl ado`** CLI, and `ADO_PM` is the PM that `grill-me` assigns information
  requests to.
- `ADO_DONE_STATE` / `ADO_DONE_ASSIGNEE` — the client's Done state and Done
  assignee, used by the [work-item lifecycle](#the-enforced-work-item-lifecycle).
- `ADO_START_STATE` / `ADO_STATE_PATH` — **0.11.0.** The client's Start state and state path. Not
  injected when unset; `ado-write` then uses `Active`.

`mcp.json` references org/project from the environment
(`${AZURE_DEVOPS_ORG_URL}` etc.), so a session automatically targets the *bound
client's* org and project — not a hardcoded one.

<Aside type="note">
Opening via the GUI is the same as `kiroctl open --dir <dir> --run` — both inject
the ADO env and launch. `kiroctl open --dir <dir>` **without** `--run` is preflight
only (it checks and prints, doesn't launch).
</Aside>

## Missions and ADO

<Aside type="note" title="0.12.0">
New in 0.12.0.
</Aside>

The fix-bug and QA missions you start from the app's **Start mission** drawer (see
[Starting a mission from the app](/workflows/missions/#starting-a-mission-from-the-app))
read and write ADO as part of the run.

### Picking the items

**Fix bugs** has an **ADO work item ids** field with a picker. The picker lists the
current sprint's open items, Bugs first. **Show all types, not only Bugs** adds the rest.
You can also type ids by hand, separated by commas. The app checks each typed id: it must
exist and must not be Closed or Removed. If the sprint has nothing open, the picker says
"No open items in the current sprint. Type ids below." The token stays on the server and
never reaches the page.

You can give ids, a bug document, or both. At least one is required.

### What a mission writes back

The confirm dialog lists every ADO write before you start. Starting is your consent
for exactly those writes.

- **Fix bugs, with ids:** the mission comments on each item and moves it to the client's
  **Done state**, assigned to the **Done assignee** (the PM when that is blank). A comment
  uses the usual Summary / Changes / Testing format and names the PR, the merge commit
  and the staging evidence. Hours stay `0`.
- **Fix bugs with a document, and every QA mission:** the mission files one Bug per
  bug in the document, or per finding. A Bug is created unassigned, in the current sprint and the project's default
  area path. It is tagged `kiro-mission` and `kiro-mission:<mission-id>`.
- **No duplicates.** Before filing, the mission looks for an open Bug tagged
  `kiro-mission` with the same fingerprint (the repo and the test case id, or the
  document's bug title). On a match it adds a comment with the new evidence instead.
- **An item moves only when its fix is live on staging.** The mission merges the PR,
  waits for the staging deploy, runs the bug's reproduction against staging, and only then
  moves the item. A fix that fails the staging check is not moved. An item the mission
  could not reproduce gets a comment with the evidence and is not moved.
- **Findings that need a decision are never moved or commented as fixed.** They stay in
  their starting state. In a `fix` QA mission, only a fixed defect ever moves.

### The Done state is required

An unattended mission can't stop to ask which state means done. So when a client has an
ADO org and project but **no Done state**, Start mission refuses **Fix bugs** and the
three QA types, which file or move bugs. The check reads "Set the done state in the ADO card." Set it in the
**Azure DevOps** card, or with `kiroctl client set-ado --done-state`.
See [Set up ADO for a client](#set-up-ado-for-a-client-org-project-pat).

### A client with no ADO

Nothing touches ADO. The check passes, the confirm dialog says "No ADO set up for this
client: bugs are recorded in the QA report only.", and the mission records its bugs in the
bug document or findings file. The **Fix bugs** type then needs a bug document, because ids
can't be fetched without ADO.

### Finding a mission's work items

Every Bug a mission files carries the tags `kiro-mission` and `kiro-mission:<mission-id>`.
Search the board for either tag to see what one mission filed.

## Reading without writing

For read-only lookups — current sprint, open work items, the epics/features
roadmap — use the sibling:

- `kiroctl ado telemetry`, or
- the **`ado-telemetry`** skill from inside a session.

<Steps>
1. Confirm the client has org, project and PAT set: `kiroctl client list` (org/project
   show inline; the PAT is stored separately).
2. Open a project bound to that client (GUI or `kiroctl open --dir <dir> --run`). Inside
   that session everything is wired — no `export` needed.
3. Pull a read-only snapshot: `kiroctl ado telemetry --json` (or just ask for sprint
   status in-session).
4. When you're ready to log work, let the agent invoke `ado-write` — don't hand-edit
   the ticket format yourself.
</Steps>
