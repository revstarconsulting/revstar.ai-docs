The skills aren't picked at random. There's a standard order for taking work
from an idea to a verified, shipped change — and a shortcut for bug-fixing when
the work is already well described. This page shows **when to use what**.

## The general path — new features and changes

```text
Planning mode  →  grill-me  →  estimation (optional)  →  Run the mission (/goal)
                                                          └─ auto-runs /qa on every
                                                             surface-changing phase
```

<Steps>

1. **Planning mode** — shape the idea into a written **plan file** (`plan.md`). Do this
   for anything non-trivial or multi-phase; the file is the artifact every later stage
   works from — grill-me hardens it, and the mission runs and audits against it.

2. **`grill-me`** — interrogate the plan adversarially until every gap and open
   decision is resolved. It works on the **plan file**: if the plan lives only in chat
   it writes `plan.md` first, then **folds each resolved decision into the file in place**
   and records a **receipt keyed to the plan's hash**. It first forces the plan into
   **phases → features** (whatever shape it arrived in) and then grills in **two
   dimensions, both deep** — a holistic pass over the cohesive whole and a per-feature
   pass over **every** feature, so a large plan gets the same rigor per decision as a
   single feature instead of going shallow. It keeps an **advisory `## Grill Coverage`
   checklist** (grouped by phase: grilled / deferred-with-reason / still-open) in the
   plan and shows it in the closing summary, and asks every question in plain English.
   The coverage checklist is a visible record, **not** a gate — it never blocks a
   mission (missions ingest pre-grilled plans and ADO items that carry no checklist).
   A plan that survives grill-me is one the mission can build without guessing — and the
   mission preflight checks the receipt, so an ungrilled (or since-edited) plan is caught.

   grill-me also **pulls RevStar's SOP standards from Mission Control** during the holistic
   pass: it works out which standards the plan implicates (data/PII handling, auth, payment
   tokens, secrets, infra…), looks each up, and **folds the applicable ones into the plan** plus
   a `## Standards` list. Those standards then ride the rest of the pipeline — the **mission
   audit** re-fetches each one *live* (the live standard is the authority) and checks the build
   against it, and **QA** derives extra test cases from them (executing what it can, flagging
   load/pen-test checks for a specialist). It's advisory and **degrades to a quiet no-op** when
   the standards service isn't reachable, so it never blocks a plan, mission, or QA run. The
   endpoint is built in; `KIRO_SOP_PROXY_URL` (or `~/.kiro/sop-standards.json`) overrides it.

   **Signing in.** The standards live behind Mission Control, so Kiro needs a sign-in. Open the
   project GUI (`kiroctl gui`) and click **"Sign in with Mission Control"** — a normal browser
   SSO login (Google Workspace). You sign in **once** and stay signed in for about a year: Kiro
   keeps the short-lived token fresh in the background, so even long unattended missions don't
   stall (it re-mints via `kiroctl sop token` when needed). Until a developer signs in, every
   standards step simply **no-ops** — it never blocks. Sign out from the same card or with
   `kiroctl sop signout`.

3. **`estimation`** *(optional)* — get the autonomous build wall-clock **plus**
   the human-oversight hours, or a quick scope/risk read. Skip it for small,
   clearly-scoped work; reach for it before committing to anything sizeable.
   AI/LLM workloads are flagged and estimated separately. A plan estimate ends with a
   required `kiro-estimate` block — see [Estimation output contract](#estimation-output-contract).

4. **Run the mission** — set the plan as the mission and drive it with `/goal`.
   It builds phase by phase and **automatically runs the `qa` skill** on every
   phase that changes product surface, so verification isn't a separate step you
   have to remember. The mission clears only when the acceptance ledger is all
   **MET**.

</Steps>

<Aside type="caution" title="The mission needs an environment">
Running QA during the mission renders pages in a **real browser**, so the
mission needs access to a **staging or dev environment** before you start it.
Without somewhere to render and exercise the app, QA can't return its two-gate
verdict (**works** *and* **matches intent**) — it silently degrades. Declare a
reachable target in the project's `qa-contract.json` when you link the project;
see [Setting up QA in a project](/workflows/qa-and-design/#setting-up-qa-in-a-project).
</Aside>

## Estimation output contract

Every **plan** estimate ends with a required, machine-checkable `kiro-estimate`
block (a fenced `kiro-estimate` code block) with all of these fields filled:

| Field | What it holds |
| --- | --- |
| `driver` | The count or scale that sets cost — e.g. `40 entities`, `3 rebuilds`. |
| `autonomous` | The range to PR-ready / build-green. |
| `supervision` | Human oversight, modelled per verifiable unit. |
| `verification` | Human verification / MATCHES-INTENT time. |
| `trust-level` | `watch-everything`, `spot-check` or `batch-on-gates`. |
| `expected` | The headline expected-case number. |
| `worst-case` | Kept separate from `expected`, never blended into it. |
| `one-way-doors` | The irreversible decisions the mission will stop for. |

The point is to make the **assumptions** behind the numbers visible, reconcilable
and gradable against the actual — not just to print a figure.

### Self-gated, advisory at preflight

After emitting a complete block, the skill runs `estimate-receipt.js write <plan>`.
It **refuses if any required field is empty**, so an incomplete estimate can't be
recorded. The receipt is keyed to the plan's hash (`sha256`), so editing the plan
invalidates it and the plan must be re-estimated — exactly like the
[grill-me receipt](/workflows/missions/#the-preflight-gate).

The mission preflight **warns, but never blocks,** when a feature mission has a
plan with no estimate on record, or a stale one. It is a separate advisory tier,
distinct from the hard blocks for a missing `grill-me`, QA environment or bug
report.

### Supervision sits beside the autonomous number

Human supervision is modelled **per verifiable unit** (phases or PRs) and presented
*beside* the autonomous number — never as a percentage of autonomous wall-clock. A
slow build inflates the clock but not what a human actually reviews. Verification
and MATCHES-INTENT is a heavier line, roughly 0.5–1 h per mission. Oversight
therefore scales with the units reviewed, not with lines of code or elapsed time.

### Reconciled across sessions

Re-estimating something already estimated loads the prior `kiro-estimate` block and
surfaces a **delta against a named assumption** rather than silently emitting a
different number. The block persists in the plan file; for ADO-tracked work it is
also posted as a gated, labelled comment on the story, so a different session can
reconcile against it. The bar is *reconciled, not identical* — LLM estimates aren't
deterministic.

### Self-calibration

Before a mission clears, its wrap captures **estimate vs actual**: the actual
autonomous time (from a per-turn-capped `activeMs` accumulator in the turn recorder,
so idle time doesn't inflate it), the units, and the human supervision and
verification minutes. It appends one row to the gitignored
`estimation-calibration.local.md` — never the committed seed — so recording a run
never dirties the pack checkout.

The committed seed `estimation-calibration.md` holds the curated live anchors the
skill reads at runtime (alongside any local rows), falling back to baked-in
bootstrap values. Saying **"recalibrate estimates"** — on demand, or when nudged
after about ten runs — promotes the accumulated local rows into updated anchors.

<Aside type="note">
The scope/risk read ("how big is this?", no plan file) is exempt: no
`kiro-estimate` block and no receipt.
</Aside>

## The bug-fixing fast path

When the bugs are **clearly described** — a document, screenshots, or concrete
repro steps — you don't need the planning → grill-me → estimation run. Go
straight to the mission with the bug-fixing prompt:

```text
Run the mission (/goal) with the bug-fixing prompt  →  /qa verifies each fix
```

The mission reproduces each reported issue, fixes it, and uses the QA protocol
to confirm the fix against the running app — retrying until it's genuinely
resolved, not trusted on say-so.

<Aside type="note">
"Clearly described" is the bar. If the bugs are vague or entangled with new
behaviour, treat it as a change and take the general path (plan → grill-me)
first — otherwise the mission is guessing at intent.
</Aside>
