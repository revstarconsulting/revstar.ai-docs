## Running QA

Say the trigger phrase and the `qa` skill runs the matching scope:

| Phrase | Scope |
| --- | --- |
| "do QA" | **Scoped:** the change and every connected part of the code (callers, and the pages, endpoints and jobs that reach it) |
| "full QA" | Complete audit of the product surface. **Runs only when you ask for it.** |
| "QA today" | Scoped, to everything changed today |

Everything else is scoped too: automatic runs after a change, the end of every mission
phase, and the run before a mission clears. Nothing switches to full on its own.

## The three non-negotiables

1. **Staging, never production.** QA runs against a staging environment, full
   stop.
2. **Every page with UI is rendered in a real browser.** A fetch or a `200`
   status is not a check — it false-passes blank heroes, covered text, broken
   contrast, and missing sections. The **`qa-render-gate`** enforces this: it
   blocks a fetch-only verification during an active QA pass and requires an
   actual render.
3. **Two-gate verdicts.** Every change-related check needs both:
   - **WORKS** — the functionality behaves correctly.
   - **MATCHES INTENT** — it's what was actually asked for.

   A change that works but isn't what was asked for is a **FAIL** — wrong
   target, wrong behavior, over-delivery, or under-delivery all count.

<Aside type="note">
Intent is written down **before** the implementation is read, so the verdict
isn't quietly rationalized around whatever got built.
</Aside>

## Building the test list mechanically

A full run doesn't enumerate the product surface in prose — it builds the test
list with scripts, so a route nobody thought to test can't slip through. Every
project declares a **`qa-contract.json`** (principals, where ownership lives, how
to read backend state, what leaves the system and where the fake sink is, and
which files declare routes), and the Phase-0 pipeline runs off it:

- **`qa-surface-inventory.js`** — walks the tree and enumerates every surface a
  human sees, classifying each into eight kinds (collection, scalar, record,
  input, artifact, transition, generated, mirrored). The output is a *floor* you
  widen, never shrink.
- **`qa-interaction-inventory.js`** — for a multi-principal app, every ownership
  entity × every write path becomes one cross-actor test point.
- **`qa-registry-merge.js`** — assembles the generated fragments into the test
  registry and emits a **prefix manifest**: the canonical test-ID set stated as
  fact, so a legitimate single-case area can't go invisible.
- **`qa-contract-validate.js`** — checks the contract against a mechanical floor,
  and hard-blocks a production target.
- **`qa-orphaned-backend.js`** — for each declared primary action, greps the declared source roots for its
  backend caller and emits a *lead* the agent adjudicates (never a hard fail), so a capability that shipped
  backend-complete but has no frontend caller surfaces as a reachability DRIFT instead of passing.
- **Two newer contract dimensions, both declaration-gated with a verdict on the coverage receipt:**
  **`data`** — per live-data page, verify the page renders the REAL producer's values (seed → capture →
  value-presence; *healthy-but-empty* is a DEFECT and *unverifiable* is never a pass, never a hand-authored
  fixture); **`reachability`** — per primary action, confirm it is reachable from the user's real entry
  page (bypass-only ⇒ DRIFT).
- **`qa-egress-probe.js`** / **`qa-case-decay.js`** — prove the fake egress sink
  is real before a run trusts it, and tier boringly-green cases into a sampled set
  so the mandatory load stays bounded across runs.

<Aside type="note">
The whole pipeline is plain Node — it runs identically on macOS, WSL and Linux.
The contract lives at the project root; start from the shipped
`qa-contract.example.json` and see the contract-conformance reference.
</Aside>

## Setting up QA in a project

A one-time setup wires the protocol into a project. Five steps:

<Aside type="caution" title="No reachable target = QA silently degrades">
QA renders and tests against the contract's `baseUrl` — it does **not** deploy
the app itself. If the run host can't reach that target — no staging/dev URL set,
no network path to it, or nothing deployed there — QA can't render, quietly
degrades, and a mission can look like it "ran QA" without actually exercising
anything. Set up a **reachable** staging/dev target when you link the project —
**before** the first mission — not after the fact.
</Aside>

**1. Declare the contract.** Copy the shipped example to the project root and edit
it for your project — principals, where ownership lives, the backend read command,
the egress sink, and which files declare routes. The contract-conformance reference
walks each field.

```sh
cp <pack>/skills/qa/references/qa-contract.example.json ./qa-contract.json
# edit it, then validate against the mechanical floor (hard-blocks a prod target):
node <pack>/bin/qa-contract-validate.js --contract ./qa-contract.json --probe
```

A `CONTRACT-OK` receipt is the confirmation; until it exists the new dimensions
report but don't gate.

<Aside type="tip" title="Let linking scaffold it">
`kiroctl` can capture the target when you link the project, so QA has a reachable
target from the very first mission:

```sh
kiroctl project set-env --dir <project> \
  --base-url https://staging.example.com --env staging --branch develop \
  --backend-query 'ssh staging-host "psql -d appdb -At -c {sql}"'
```

The GUI's **New project** wizard has a QA step that captures the same fields —
staging/dev URL, environment, target branch, and backend (SSH/DB) access — and
the project detail's **QA environment** card lets you edit them any time after.
Linking scaffolds a minimal `qa-contract.json` and a `qa-test-cases/test-credentials.md`
stub (list your test users there), and **never overwrites** a contract you've
hand-authored. The target branch is injected as `TARGET_BRANCH` for the mission,
and `kiroctl doctor --dir <project>` WARNs until a reachable target is set.
</Aside>

**2. Build the test list.** On a full run the `qa` skill runs the Phase-0 pipeline
for you (surface + interaction inventories → `qa-registry-merge.js` → the prefix
manifest). You can also run them by hand from the project root while iterating on
the contract.

**3. Arm the gates.** Gates are inert until an enable flag exists (the exceptions are the always-on
`telemetry-emit` hook and, wherever Mobile Next is configured, `mobile-guard` and `mobile-sweep`) — globally at
`$KIRO_HOME/gates/<gate>.enabled` or per-project at `<project>/.kiro/gates/`. Arm
one at a time:

```sh
touch ~/.kiro/gates/qa-render-gate.enabled     # block fetch-instead-of-render during QA
touch ~/.kiro/gates/qa-report-gate.enabled     # block a report missing verdicts/receipt
# optional, opt-in: block a mission-touched surface with no test case
touch ~/.kiro/gates/qa-surface-gate.enabled
```

**4. Wire the deterministic teeth.** `ci/qa-gate.sh` recomputes the coverage
receipt and exits non-zero on `COVERAGE-FAIL`. Add it to CI, or as a git pre-push
hook:

```sh
ln -s ../../ci/qa-gate.sh .git/hooks/pre-push
```

**5. Run it.** Say **"do QA"** for a scoped run or **"full QA"** for a complete
audit. The skill creates its own `.qa-active` sentinel (which arms the render gate),
follows the protocol, and writes the report + coverage receipt.

<Aside type="note">
Everything is Node + POSIX `sh` — the same setup works on macOS, WSL and Linux. The
pack ships the scripts; you only add the project's `qa-contract.json`, the gate
flags you want armed, and the CI hook.

QA renders every UI page in a **real browser** (never a fetch) and captures
**screenshots** as the evidence. The browser runs **invisibly wherever a visible
one would disrupt you**: under a virtual framebuffer on **display-less Linux**
(install Xvfb — `sudo apt-get install -y xvfb` — and the pack auto-wraps the
Playwright MCP in `xvfb-run`), and **headless on macOS** (a headed macOS window
activates and steals keyboard focus on every navigation, locking you out of what
you're typing). On **Windows** and desktop Linux it renders headed-visible.
Headless is **not** a downgrade — it's the same engine with identical layout,
overlay and contrast, and the screenshots are the proof regardless.
</Aside>

## Scoped runs: the change and everything connected to it

A scoped run doesn't guess what the change affected. It works it out from git and
tests every connected part of the code:

- **What changed:** everything since your branch left the staging branch (or the
  repo's default branch), plus uncommitted and new files. Inside a mission it's
  measured from the mission's start when that's older, so work committed straight
  onto staging still counts.
- **What's connected:** followed through the imports all the way out, in JS/TS/JSX,
  Python, Go and C#, and across the project's repos — a changed API endpoint pulls in
  the front-end code that calls it, in whichever repo it lives. A project repo that
  isn't cloned is reported as *callers unknown*, never "no callers".
- **What gets tested:** the places a user or system actually reaches — pages and
  routes, API endpoints, app screens, background jobs, webhooks, CLIs — each with the
  chain that explains why it's in (`page /teachers ← TeacherList ← lookupTeacher
  (changed)`). For a connected page the test drives that exact path and re-runs the
  page's existing cases; a page load alone doesn't count.
- **Wrappers count:** a component in a file-router layout (Expo Router `_layout`, Next.js
  `layout`) reaches every screen or page under that layout, and a script a plain HTML page
  loads with `<script src>` reaches that page. Code that reaches no entry point at all
  (build config, dead code, DI wiring) is listed as an **unclassified** target, so it still
  gets a look instead of silently dropping out.

The agent records each result through one script, which also notes the code each test
ran against:

```sh
node <pack>/bin/qa-scoped-record.js begin                 # lists the targets; prints a runId
node <pack>/bin/qa-scoped-record.js pass --run <runId> --target "<id>" --works yes --intent yes --method live --evidence <screenshot>
node <pack>/bin/qa-scoped-record.js end --run <runId>     # sends the run's QA result to Mission Control
node <pack>/bin/qa-scoped-record.js status                # what's tested, waived, or stale
```

When a change reaches **more than 25** targets, the run doesn't stop to ask. The agent
tests at least a third of them (10 minimum; all of them when there are 10 or fewer),
including a tested target of every kind each changed item reaches, and waives the rest
— each waiver names a tested **stand-in** of the same kind that reaches the same changed
code. Mobile screens are tested together in as few device bookings as possible, and the
agent never raises the minute cap.

**Before a mission can clear**, the [fan-out gate](/capabilities/gates/#the-qa-fan-out-gate)
checks all of this against the mission's whole diff.

## What a QA report must contain

On top of the two verdicts, the `qa-report-gate` now refuses a report when:

- a verdict has no **`method: live | inspection | code`**, or a PASS was reached only by
  reading code or inspecting it. Those are provisional: exercise it live, or, only when
  staging genuinely can't reach it, tag `[cannot-exercise-on-staging]` with what staging
  lacks (it then counts as waived, not tested);
- a line says **PASS and describes a problem** ("PASS but the label is cut off"). An issue
  you can describe is a FAIL;
- a run with change items doesn't cite its **adversarial-pass receipt**: the agent keeps
  trying to break the *changed* items until two rounds in a row find nothing new
  (`qa-adversarial-receipt.js record --round <n> --findings <k>`);
- a full run cites no **coverage receipt file**, or one made with loosened thresholds.

These checks apply to QA runs started after the update; earlier runs keep the old rules.

## Full-run coverage

A full QA run has to prove it actually covered everything, not just assert it
did. **`qa-coverage-receipt.js`** is the coverage oracle: it reconciles the
ledger of what was tested against the registry and the prefix manifest and emits
`COVERAGE-OK` only when every item is accounted for. It blocks on orphaned test
IDs, a verdict on a test that never ran, too many not-executed cases, coverage
below the bar, uninspected routes, **manifest drift** (a case missing from the
canonical set), and — when the surface gate is armed — a surface the mission
*touched* that carries no test case. Retired and sampled-decay cases are excluded
from the denominator and reported separately, never silently dropped.

The **`qa-report-gate`** blocks a written QA report that's missing intent
verdicts, render evidence, or the receipt's result line. A full run that ended
below the floor can still be written if it carries the receipt's own
`COVERAGE-FAIL: …` line with its reasons, so the honest result is kept and can't
be read as complete. And because Kiro's stop
hook can't hard-block, **`ci/qa-gate.sh`** gives the same teeth a second home: it
recomputes the receipt and exits non-zero on `COVERAGE-FAIL`, so a CI job or a git
pre-push hook stops a change that would ship with orphaned cases.

## Definition of done

Done means a **filed, human-verified checklist** — not the agent's own say-so.
The agent that built or fixed something cannot self-certify that it's QA'd;
the checklist has to be produced and then actually verified against the running
app.

<Aside type="caution">
"The data doesn't exist" is never a skip reason. Create the test data, run the
check, clean it up afterward.
</Aside>

## The `design` skill

Reach for `design` when building or changing any front-end surface —
components, layouts, pages, forms, flows, styles, or theme. It:

- **Builds to the project's design authority** — the plan's pinned `## Design Authority`
  (a customer mockup in *fidelity* mode, or the committed **brand guide** in *consistency*
  mode) — rather than inventing a second design language. The brand guide
  (`.kiro/context/brand-guide.md`) is the captured, reviewed source-of-truth.
- Enforces the **full component state set** for every component:
  - default
  - hover
  - focus
  - disabled
  - loading
  - empty
  - error

Loading, empty, and error are the three that hide dead-ends — a component that
only has its default state looks finished and isn't. `design` builds it right;
QA proves the states exist and lead somewhere.

## Design authority & the brand guide

A plan's UI can drift two ways — a build that **redesigns** a customer's provided look, or new UI
that ships **off-brand** from the rest of the app. Both used to pass QA. The design-fidelity thread
closes that, end to end:

- **`grill-me` pins a `## Design Authority`** for any UI plan — *fidelity* (reproduce the customer
  mockup's design language) or *consistency* (match the project brand guide). It pins the design
  **language** (tokens, component styling + states, layout, icon/motion); the **content** still
  evolves freely through grilling.
- **The `brand-guide` skill** captures the app's design language into a committed, reviewed
  `.kiro/context/brand-guide.md` — generated from the codebase design system crossed with the
  rendered app, with any inconsistencies surfaced for you to arbitrate. First run on a UI project
  prompts to generate it; it's the source-of-truth the `design` skill builds to.
- **QA enforces it.** For a UI change with a Design Authority, QA compares the rendered build's
  design language against the authority (token/component conformance, **not** a pixel diff — content
  differences don't count). A mismatch is a **FAIL that drives the normal QA↔mission fix loop**: the
  build is restyled to the authority and re-QA'd, and the mission can't clear until it conforms.

## Native mobile apps

A repo whose `qa-contract.json` has a `mobile` block is tested on real iOS and
Android devices through Mobile Next, not in a browser. The QA rules above still
hold (staging only, two-gate verdicts, screenshot evidence). Setup, the device
cost safeguards, and the limits are in [Mobile app QA](/workflows/mobile-qa/).
A mobile run writes `mobile` on line 2 of the `.qa-active` sentinel, which
marks it as a device run for the QA gates.

## Code-only work is a different lane

Work with no product surface — tooling, internal scripts, backend-only logic
with no UI impact — is verified by its own test suite (red-green: a failing
test that now passes, and the adjacent case re-checked), not by the browser
protocol above. Don't run a full QA reconciliation against product test
coverage for a change the product surface never touched.
