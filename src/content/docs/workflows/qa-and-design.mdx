## Running QA

Say the trigger phrase and the `qa` skill runs the matching scope:

| Phrase | Scope |
| --- | --- |
| "do QA" | **Scoped:** the change and every connected part of the code (callers, and the pages, endpoints and jobs that reach it) |
| "full QA" | Complete audit of the product surface. **Runs only when you ask for it, or when the plan says so** (see below). |
| "QA today" | Scoped, to everything changed today |

Everything else is scoped too: automatic runs after a change, the end of every mission
phase, and the run before a mission clears. Nothing switches to full on its own.

**0.12.0.** Starting a [QA mission](#qa-missions) is also an explicit ask for full QA.
### Full QA from the plan

The other way to get a full run is to agree on it while planning. `grill-me` asks once per
plan whether the plan needs a full regression. It checks five triggers itself and recommends
full when any one applies:

1. a go-live or a major release;
2. a change to sign-in, roles or permissions, payments or billing, the data model or a
   migration, or app-wide navigation;
3. a framework, dependency, build or infrastructure change, whose reach the code
   connections don't show;
4. many features at once: more than a third of the plan's features, or more than five;
5. no full regression has ever run on the project.

It shows the evidence, recommends, and you decide. `pm-grill-me` asks a product-worded
version that covers triggers 1, 2 and 4. The answer goes into the plan:

```
## QA Scope
scope: full
reason: first production launch
triggers: 1
```

- **The scope is frozen when the mission starts.** `mission-state.js --init` reads the section
  once, and every session shows a `QA scope: …` line. Editing the plan mid-build changes
  nothing; if you change your mind, say "full QA". A section it can't read falls back to
  scoped, and the fallback is shown every session.
- **The full run is the mission's last QA step,** after the last code change. It covers the
  whole project, with one run per mobile app. It also records the fan-out results, so
  connected items it didn't reach still get their scoped test.
- **The mission can't clear without the full run.** For a full mission, `--clear` needs a
  full-run coverage receipt written after the last code change. COVERAGE-FAIL counts too:
  it is printed and kept in the closing summary instead of blocking the mission.
- **The estimate counts it.** A full run is its own line in the estimate: per run, per app,
  plus review time.

## The three non-negotiables

1. **Staging, never production.** QA runs against a staging environment, full
   stop.
2. **Every page with UI is rendered in a real browser.** A fetch or a `200`
   status is not a check — it false-passes blank heroes, covered text, broken
   contrast, and missing sections. The **`qa-render-gate`** enforces this: it
   blocks a fetch-only verification during an active QA pass and requires an
   actual render.
3. **Two-gate verdicts.** Every change-related check needs both:
   - **WORKS** — the functionality behaves correctly.
   - **MATCHES INTENT** — it's what was actually asked for.

   A change that works but isn't what was asked for is a **FAIL** — wrong
   target, wrong behavior, over-delivery, or under-delivery all count.

<Aside type="note">
Intent is written down **before** the implementation is read, so the verdict
isn't quietly rationalized around whatever got built.
</Aside>

## Building the test list mechanically

A full run doesn't enumerate the product surface in prose — it builds the test
list with scripts, so a route nobody thought to test can't slip through. Every
project declares a **`qa-contract.json`** (principals, where ownership lives, how
to read backend state, what leaves the system and where the fake sink is, and
which files declare routes), and the Phase-0 pipeline runs off it:

- **`qa-surface-inventory.js`** — walks the tree and enumerates every surface a
  human sees, classifying each into eight kinds (collection, scalar, record,
  input, artifact, transition, generated, mirrored). The output is a *floor* you
  widen, never shrink.
- **`qa-interaction-inventory.js`** — for a multi-principal app, every ownership
  entity × every write path becomes one cross-actor test point.
- **`qa-registry-merge.js`** — assembles the generated fragments into the test
  registry and emits a **prefix manifest**: the canonical test-ID set stated as
  fact, so a legitimate single-case area can't go invisible.
- **`qa-contract-validate.js`** — checks the contract against a mechanical floor,
  and hard-blocks a production target.
- **`qa-orphaned-backend.js`** — for each declared primary action, greps the declared source roots for its
  backend caller and emits a *lead* the agent adjudicates (never a hard fail), so a capability that shipped
  backend-complete but has no frontend caller surfaces as a reachability DRIFT instead of passing.
- **Two newer contract dimensions, both declaration-gated with a verdict on the coverage receipt:**
  **`data`** — per live-data page, verify the page renders the REAL producer's values (seed → capture →
  value-presence; *healthy-but-empty* is a DEFECT and *unverifiable* is never a pass, never a hand-authored
  fixture); **`reachability`** — per primary action, confirm it is reachable from the user's real entry
  page (bypass-only ⇒ DRIFT).
- **`qa-egress-probe.js`** / **`qa-case-decay.js`** — prove the fake egress sink
  is real before a run trusts it, and tier boringly-green cases into a sampled set
  so the mandatory load stays bounded across runs.

<Aside type="note">
The whole pipeline is plain Node — it runs identically on macOS, WSL and Linux.
The contract lives at the project root; start from the shipped
`qa-contract.example.json` and see the contract-conformance reference.
</Aside>

## Setting up QA in a project

A one-time setup wires the protocol into a project. Five steps:

<Aside type="caution" title="No reachable target = QA silently degrades">
QA renders and tests against the contract's `baseUrl` — it does **not** deploy
the app itself. If the run host can't reach that target — no staging/dev URL set,
no network path to it, or nothing deployed there — QA can't render, quietly
degrades, and a mission can look like it "ran QA" without actually exercising
anything. Set up a **reachable** staging/dev target when you link the project —
**before** the first mission — not after the fact.
</Aside>

**1. Declare the contract.** Copy the shipped example to the project root and edit
it for your project — principals, where ownership lives, the backend read command,
the egress sink, and which files declare routes. The contract-conformance reference
walks each field.

```sh
cp <pack>/skills/qa/references/qa-contract.example.json ./qa-contract.json
# edit it, then validate against the mechanical floor (hard-blocks a prod target):
node <pack>/bin/qa-contract-validate.js --contract ./qa-contract.json --probe
```

A `CONTRACT-OK` receipt is the confirmation; until it exists the new dimensions
report but don't gate.

<Aside type="tip" title="Let linking scaffold it">
`kiroctl` can capture the target when you link the project, so QA has a reachable
target from the very first mission:

```sh
kiroctl project set-env --dir <project> \
  --base-url https://staging.example.com --env staging --branch develop \
  --backend-query 'ssh staging-host "psql -d appdb -At -c {sql}"'
```

The GUI's **New project** wizard has a QA step that captures the same fields —
staging/dev URL, environment, target branch, and backend (SSH/DB) access — and
the project detail's **QA environment** card lets you edit them any time after.
**0.11.0.** The card saves the backend query and probe to the machine-local
`.kiro/qa-contract.local.json`, not the committed contract (see
[Values that differ per machine](#values-that-differ-per-machine)).
Linking scaffolds a minimal `qa-contract.json` and a `qa-test-cases/test-credentials.md`
stub (list your test users there), and **never overwrites** a contract you've
hand-authored. The target branch is injected as `TARGET_BRANCH` for the mission,
and `kiroctl doctor --dir <project>` WARNs until a reachable target is set.
</Aside>

**2. Build the test list.** On a full run the `qa` skill runs the Phase-0 pipeline
for you (surface + interaction inventories → `qa-registry-merge.js` → the prefix
manifest). You can also run them by hand from the project root while iterating on
the contract.

**3. Arm the gates.** The four safe hooks and, from 0.11.0, `mission-state-protect` are already armed by the installer. The blocking gates are inert until an enable flag exists (the exceptions are the always-on
`telemetry-emit` hook, `mission-pause` and, wherever Mobile Next is configured, `mobile-guard` and `mobile-sweep`) — globally at
`$KIRO_HOME/gates/<gate>.enabled` or per-project at `<project>/.kiro/gates/`. Arm
one at a time:

```sh
touch ~/.kiro/gates/qa-render-gate.enabled     # block fetch-instead-of-render during QA
touch ~/.kiro/gates/qa-report-gate.enabled     # block a report missing verdicts/receipt
# optional, opt-in: block a mission-touched surface with no test case
touch ~/.kiro/gates/qa-surface-gate.enabled
```

**4. Wire the deterministic teeth.** `ci/qa-gate.sh` recomputes the coverage
receipt and exits non-zero on `COVERAGE-FAIL`. Add it to CI, or as a git pre-push
hook:

```sh
ln -s ../../ci/qa-gate.sh .git/hooks/pre-push
```

**5. Run it.** Say **"do QA"** for a scoped run or **"full QA"** for a complete
audit. The skill creates its own `.qa-active` sentinel (which arms the render gate),
follows the protocol, and writes the report + coverage receipt.

<Aside type="note">
Everything is Node + POSIX `sh` — the same setup works on macOS, WSL and Linux. The
pack ships the scripts; you only add the project's `qa-contract.json`, the gate
flags you want armed, and the CI hook.

QA renders every UI page in a **real browser** (never a fetch) and captures
**screenshots** as the evidence. The browser runs **invisibly wherever a visible
one would disrupt you**: under a virtual framebuffer on **display-less Linux**
(install Xvfb — `sudo apt-get install -y xvfb` — and the pack auto-wraps the
Playwright MCP in `xvfb-run`), and **headless on macOS** (a headed macOS window
activates and steals keyboard focus on every navigation, locking you out of what
you're typing). On **Windows** and desktop Linux it renders headed-visible.
Headless is **not** a downgrade — it's the same engine with identical layout,
overlay and contrast, and the screenshots are the proof regardless.

The workbench maintainer's own macOS release checks run on a rented Mac: see
[macOS QA lane (NoMac)](/workflows/mac-lane/).
</Aside>

### Values that differ per machine

**0.11.0.** Some contract values are yours alone: your own AWS profile, an SSH alias, a local
path. Keep those out of the committed `qa-contract.json`.

**The local file.** `<repo>/.kiro/qa-contract.local.json` is merged over `qa-contract.json` by every
pack reader. Objects merge by key. Arrays and plain values in the local file replace the committed
ones. A local file that isn't valid JSON is reported as a problem that names the file.

```json
{
  "backend": { "probe": "aws sts get-caller-identity --profile my-profile" }
}
```

- **The app saves Backend access there.** The project's QA environment card writes the backend query
  and probe to the local file, not to the committed contract. An older committed value that equals
  what the app manages is moved to the local file on the next save. A different value you set by hand
  is left alone.
- **It is not committed.** `kiroctl`'s managed `.gitignore` block now lists
  `.kiro/qa-contract.local.json` and `.qa-gate/`.

**Per-platform probes.** Any probe can be a string or an object with one command per platform:

```json
{
  "backend": {
    "probe": {
      "default": "psql -d appdb -Atc 'select 1'",
      "win32": "psql.exe -d appdb -Atc \"select 1\"",
      "darwin": "/opt/homebrew/bin/psql -d appdb -Atc 'select 1'"
    }
  }
}
```

This works for `backend.probe`, `egress[].probe`, `access.stagingProbe`, the `probe` of each
`access` token, deploy, paid API and custom entry, and `access.qaLogin.probe`. This machine's
platform (`win32`, `darwin` or `linux`) is used first, then `default`. When neither exists, the
probe counts as **not declared on this machine**, and the message gives the exact
`"<platform>": "<command>"` line to add. A `backend.query` that contains `{sql}` and is used as a
probe now runs with `SELECT 1` in its place.

**The backend can name what it covers.** `backend` takes `"covers": "<plan dependency id>"`, the
same as an access entry (see [Access: you must declare it](/workflows/missions/#access-you-must-declare-it)).

**The contract check's receipt.** `qa-contract-validate.js` writes `.qa-gate/close-receipts/contract.json`
under the **project root**: the folder that holds the contract, or `--root`. It never writes it in the
folder you ran the command from. Every `.qa-gate/` folder now holds a `.gitignore` containing `*`, so
QA receipts never appear in `git status`. No repo `.gitignore` is edited for this.

**Lane URL.** When a mission holds a [lane](/workflows/missions/#missions-in-a-lane) whose
`.mission-lane` has an `app_url`, QA uses that URL instead of the contract's `baseUrl`.

## Scoped runs: the change and everything connected to it

A scoped run doesn't guess what the change affected. It works it out from git and
tests every connected part of the code:

- **What changed:** the same diff a pull request shows. That is everything since your
  branch left the branch it merges into, plus uncommitted and new files. On the
  integration branch itself, it's everything since the mission started.
- **What's connected:** followed through the imports all the way out, in JS/TS/JSX,
  Python, Go and C#, and across the project's repos — a changed API endpoint pulls in
  the front-end code that calls it, in whichever repo it lives. A project repo that
  isn't cloned is reported as *callers unknown*, never "no callers".
- **What gets tested:** the places a user or system actually reaches — pages and
  routes, API endpoints, app screens, background jobs, webhooks, CLIs — each with the
  chain that explains why it's in (`page /teachers ← TeacherList ← lookupTeacher
  (changed)`). For a connected page the test drives that exact path and re-runs the
  page's existing cases; a page load alone doesn't count.
- **Wrappers count:** a component in a file-router layout (Expo Router `_layout`, Next.js
  `layout`) reaches every screen or page under that layout, and a script a plain HTML page
  loads with `<script src>` reaches that page. Code that reaches no entry point at all
  (build config, dead code, DI wiring) is listed as an **unclassified** target, so it still
  gets a look instead of silently dropping out.
- **Lazy-loaded pages:** **0.11.0.** A page loaded through any wrapper around
  `() => import('./Page')` is treated like `React.lazy`. That covers `lazyImportRetry(() => import('./Page'))`
  and `utils.lazyRetry(...)`. A change to a component only one page uses selects only that page.
  `.then(m => m.Named)` binds the named export. A wrapper that takes a path string, such as
  `lazyPage('./pages/X')`, is listed in the contract:
  `"impact": { "lazyWrappers": ["lazyPage"] }`.

**Which branch it measures against.** The first of these that is set and exists wins:

1. The mission's base branch: `build-plan` and `fix-bugs` pass it to `mission-state.js --init --base-branch <branch>`. It is fixed per repo for the whole mission.
2. The project's **Target branch**: the field in the app's QA environment card, or `kiroctl project set-env --dir <p> --branch dev`.
3. The repo's `qa-contract.json` `integrationBranch`.
4. Otherwise the closest of `staging`, `dev`, `develop`, the remote's default branch, `main` and `master`.

Set the Target branch on any project that works on `dev` but still has an old `staging`
branch; otherwise the guess can pick stale `staging` and QA hundreds of changes that
aren't yours. The merge base is worked out again on every run, so merging the latest
`dev` into your branch mid-mission doesn't add its changes to QA. If the merge base is
more than 50 commits behind the mission start, QA uses the mission start instead.

Every run prints one line per repo so you can check it:

```text
base web: dev via mission -> 3f2a91c04 (merge-base), HEAD is 4 commits ahead
```

The agent records each result through one script, which also notes the code each test
ran against:

```sh
node <pack>/bin/qa-scoped-record.js begin                 # lists the targets; prints a runId
node <pack>/bin/qa-scoped-record.js pass --run <runId> --target "<id>" --works yes --intent yes --method live --evidence <screenshot>
node <pack>/bin/qa-scoped-record.js end --run <runId>     # sends the run's QA result to Mission Control
node <pack>/bin/qa-scoped-record.js status                # what's tested, waived, or stale
```

The record lives in `.qa-gate/scoped/` as an append-only log, so writing a verdict stays
fast on long missions. Each write takes a short lock, so parallel QA sub-agents can record
at the same time without losing verdicts. Records from earlier versions are still read.

When a change reaches **more than 25** targets, the run doesn't stop to ask. The agent
tests at least a third of them (10 minimum; all of them when there are 10 or fewer),
including a tested target of every kind each changed item reaches, and waives the rest
— each waiver names a tested **stand-in** of the same kind that reaches the same changed
code. Mobile screens are tested together in as few device bookings as possible, and the
agent never raises the minute cap.

**Before a mission can clear**, the [fan-out gate](/capabilities/gates/#the-qa-fan-out-gate)
checks all of this against the mission's whole diff. It finds the mission's repos from the
mission index, so it works from a git worktree or a second repo, and a mission whose repos
can't be found is refused rather than waved through (`--repos <paths>` names them,
`--no-repos` says no code changed).

QA of the RevStar.ai app itself: an agent can't read the app's token log. Use
`kiroctl gui --qa-url`, which prints a one-time URL for the QA browser from the running
app. It is refused while all agents are stopped or the mission is paused.

## Delivery capture

<Aside type="note" title="0.12.2">
New in 0.12.2. Before, QA wrote a verdict and a screenshot path and nothing a person could follow later.
</Aside>

In a mission that produces [delivery docs](/workflows/missions/#delivery-docs), QA also records what it saw
in a form the UAT guide can use. Right after it records a changed target's `pass` or `fail`, the agent runs:

```sh
node <pack>/bin/qa-scoped-record.js capture --run <id> --target <id> --data <capture.json>
```

The command writes `delivery/capture/<mission-id>/<feature>.json`. It does nothing outside a delivery-docs
mission: it prints `capture: off (...) -- nothing written` and exits 0, so **ad-hoc QA is unchanged**. It
also does nothing when `mission-docs.disabled` applies (see [Delivery docs](/workflows/missions/#delivery-docs)).

Two parts come from QA's own verdict and cannot be set by hand: the result (`runId`, `target`, `works`,
`intent`, `method`) and the screenshots. The capture refuses to write unless the verdict was recorded with at
least one screenshot that exists on disk as its `--evidence`. The agent writes the rest in plain English:

| Field | What it holds |
| --- | --- |
| `featureName` | The feature as a person would name it. |
| `intentStatement` | What the user can do now, from the item's intent statement. |
| `navPath` | The labels a user clicks to get there, in order. |
| `steps` | Each step as an action and its expected result. At least one is a negative step, such as a wrong role or missing data. |
| `successCriteria` | How the tester knows it worked. |
| `roles` | The roles the agent tested as. |
| `switches` | A flag or setting that changes the behaviour: its name, where it lives and its state. |

**Never a password.** The agent never puts a password, token or secret in the file. The command refuses a
`--data` file that has a password-like key in it, and the UAT guide shows test-account usernames only. A connected target whose intent is "behaves as
before" needs no capture.

## What a QA report must contain

On top of the two verdicts, the `qa-report-gate` now refuses a report when:

- a verdict has no **`method: live | inspection | code`**, or a PASS was reached only by
  reading code or inspecting it. Those are provisional: exercise it live, or, only when
  staging genuinely can't reach it, tag `[cannot-exercise-on-staging]` with what staging
  lacks (it then counts as waived, not tested);
- a line says **PASS and describes a problem** ("PASS but the label is cut off"). An issue
  you can describe is a FAIL;
- a run with change items doesn't cite its **adversarial-pass receipt**: the agent keeps
  trying to break the *changed* items until two rounds in a row find nothing new
  (`qa-adversarial-receipt.js record --round <n> --tried "<what>" --result "<what happened>" --findings <k>`).
  **0.11.0:** each round now says what was tried (`--tried`, 20 characters or more) and what
  happened (`--result`, 10 or more), and `--fixed` records the commit or note for a round with findings.
  An empty round counts only if it carries a `tried`, so a receipt recorded by an older pack, whose rounds
  have none, reads as not finished and needs two new rounds;
- a full run cites no **coverage receipt file**, or one made with loosened thresholds.

These checks apply to QA runs started after the update; earlier runs keep the old rules.

## Full-run coverage

A full QA run has to prove it actually covered everything, not just assert it
did. **`qa-coverage-receipt.js`** is the coverage oracle: it reconciles the
ledger of what was tested against the registry and the prefix manifest and emits
`COVERAGE-OK` only when every item is accounted for. It blocks on orphaned test
IDs, a verdict on a test that never ran, too many not-executed cases, coverage
below the bar, uninspected routes, **manifest drift** (a case missing from the
canonical set), and — when the surface gate is armed — a surface the mission
*touched* that carries no test case. Retired and sampled-decay cases are excluded
from the denominator and reported separately, never silently dropped.

The **`qa-report-gate`** blocks a written QA report that's missing intent
verdicts, render evidence, or the receipt's result line. A full run that ended
below the floor can still be written if it carries the receipt's own
`COVERAGE-FAIL: …` line with its reasons, so the honest result is kept and can't
be read as complete. And because Kiro's stop
hook can't hard-block, **`ci/qa-gate.sh`** gives the same teeth a second home: it
recomputes the receipt and exits non-zero on `COVERAGE-FAIL`, so a CI job or a git
pre-push hook stops a change that would ship with orphaned cases.

## QA missions

<Aside type="note" title="0.12.0">
New in 0.12.0.
</Aside>

A **QA mission** runs a full QA audit as an enforced, pre-approved mission, with a ledger and a clear that
can't be skipped. Start one from the app's **Start mission** drawer (**QA full**, **QA full + fix** or
**Regression suite**), or type `/qa-mission variant=full|fix|regression` in a v2 `dev` chat. The mission
kind is `qa`. It needs no plan, no grill receipt and no bug document, and its QA scope is `full` by the kind itself.

All three variants share one first step, the **spine**: the `qa` skill in full mode, exactly as written
there. It is the coverage audit, the rebuild of the complete test registry, every case run, and the coverage
receipt. `qa-mission` never restates it, so full QA has one definition.

| Variant | After the spine |
| --- | --- |
| `full` | Nothing. The report and the coverage receipt are the deliverable. |
| `fix` | Triage every finding. Fix the defects, land the fixes through a PR into the base branch, wait for the staging deploy, re-test on staging. Findings that need a decision are listed, not changed. |
| `regression` | Turn the registry into scripted tests, in a repo, optionally wired into CI/CD. |

Every variant files the findings as ADO Bugs when the client has ADO, and records them in a findings file,
`qa-test-cases/qa-mission-<mission-id>-findings.md`, either way. See
[Azure DevOps power](/workflows/azure-devops/#missions-and-ado).

### The `fix` variant

The mission triages each finding as a **defect** (broken against the app's own evident intent: an error, a
dead link, a crash, a contrast failure, a dead end) or **needs a decision** (a behaviour, copy or product call,
or missing access). It fixes defects the way `fix-bugs` does: reproduce first, fix at the owning layer,
re-verify, and sweep for the same flaw elsewhere. A needs-decision finding is never touched. It becomes a
`needs-decision:<finding-id>` criterion with its triage, and the mission ends **PARTIAL** and lists each one.
The completion verifier re-reads every triage and fails the audit on one that is plainly a defect, so this
isn't a way to leave a bug unfixed. See [Clearing a mission](/workflows/missions/#clearing-a-mission).

### Estimate first

With **Estimate first, then ask me** (`estimate-first=yes`), the mission pauses after its planning and before
it runs any case. It reports the number of cases, the device minutes and the Kiro credits, each with its
source, and waits for you to approve in the app. See
[Approving an estimate](/workflows/missions/#approving-an-estimate).

When the mission clears, it adds one estimate-versus-actual row to the estimation calibration log by itself.
The actual Kiro credits read **UNMEASURED** when the chat exposes no metering, which is the case in an
interactive chat. Nothing invents a number.

### The full-run gate

A mission can't clear a full run unless the coverage receipt is newer than the last code change. For `full`
that rule is unchanged. `fix` and `regression` change code after the spine finishes, so for those two
variants the spine's own coverage receipt satisfies the gate. Each closes with its own check in its place:
`fix` with a scoped QA over the fix diff, plus a passing re-test per fixed finding. `regression` with the
suite itself running green against staging.

### The regression suite

The `regression` variant writes **programmatic tests, not model-driven ones**. Web tests use Playwright Test.
Mobile tests use **Mobilewright** on Mobile Next cloud devices. It is "Playwright for mobile": real locators,
auto-wait and retrying assertions, with no model call. Both suites have the same API shape.

- **Gap-only.** The mission maps every registry case to any test that already covers it, across every repo of
  the project, and writes new tests only for the cases nothing covers. The map is the catalog
  `qa-reports/ci-regression-candidates.md`: one row per case, with its status, a pointer to its test and
  why it wasn't covered. This is what `/ci-qa-coverage` used to produce on its own.
- **Where the tests go.** Into `repo=<name>`, a repo of the project, in its existing e2e location if it has
  one, else `tests/regression/web` and `tests/regression/mobile`. Or into `new-repo=<org>/<name>`: a new
  private GitHub repo, with no collaborators added, mapped into the project. Either way the suite lands
  through a PR, never a direct push.
- **Credentials.** Tests read them from the environment at run time (`QA_<ACCOUNT>_PASSWORD`, `QA_BASE_URL`).
  A value is never written into a test, a config or a log.
- **Known bugs.** A test for something the audit found broken is written correctly and marked expected-to-fail
  (`test.fail()`), with its ADO Bug id in the title. A marked test that starts passing is flagged so the mark
  can go. The mission never weakens an assertion to make it pass, never skips the test, and never fixes the
  bug. That is the `fix` variant.
- **Cannot be automated.** A case is listed that way only for one of five reasons: `captcha`,
  `external-inbox`, `third-party-hosted`, `visual-judgement` or `prod-only-data`. Each entry also says what
  would make it automatable. The verifier rejects any other reason. "It is hard" isn't one.
- **CI/CD, only when asked (`ci=yes`).** The mission uses the CI system the project already has, found by
  `kiroctl ci-detect`. It never adds a new one. When there is more than one, the line must name it with
  `ci-system=`. It wires exactly what the line says: `web-runs` and `mobile-runs` are each `pr` (every PR or
  commit), `nightly` or `manual`, with no default. A mobile CI job has no ledger, so its pipeline timeout is the
  client's full-run device-minute cap, and a final step always releases its devices.
- **CI secrets, value-blind.** The `secrets=NAME:from,...` argument names each CI secret and the local source
  it comes from. The agent never sees a value. `kiroctl ci-secret` copies each one from the local secret store
  into the CI secret store inside kiroctl, and its output shows names only. The names follow the RevStar secrets
  standard: least privilege, scoped to the suite's repo or pipeline, read by the pipeline at run time, and
  never committed. When a secret can't be set from here (the probe says no, or the system is GitLab,
  Bitbucket or Jenkins), the mission finishes everything else, opens the PR, and ends **BLOCKED** with the exact
  list of names and where a person must add them. The block is a declared dependency (`--declare-dep`) whose check
  fails while any secret is missing, so it clears itself once a person adds them.
- **Mobile device runs.** Every scripted mobile run goes through `mobile-qa.js run`, which books the devices,
  records them in the billing ledger and always releases them. The budget is **mission-wide**: see
  [Scripted device runs](/workflows/mobile-qa/#scripted-device-runs). Tests the budget stopped are reported
  "written, not run on a device", and the mission ends **PARTIAL** with a `budget-exhausted:mobile` criterion.

The suite is done when every uncovered case has a scripted test or an allowed reason, every covered case points
to its test, the suite is green against staging locally (marked known-bug tests failing as expected counts as
green), the CI run is green when CI is on, and the suite is in a PR.

### Two files the report gate does not judge

The `qa-report-gate` treats every file under `qa-reports/` as a QA report. Two exact names are exempt,
because each is an input or a catalog and carries no verdicts: `qa-reports/fix-bugs-<mission-id>.md`
(the bug document `/fix-bugs ado=` writes) and `qa-reports/ci-regression-candidates.md`. Nothing else is exempt.
A QA mission's findings file lives in `qa-test-cases/` for that reason. See
[Gates](/capabilities/gates/).

## Definition of done

Done means a **filed, human-verified checklist** — not the agent's own say-so.
The agent that built or fixed something cannot self-certify that it's QA'd;
the checklist has to be produced and then actually verified against the running
app.

<Aside type="caution">
"The data doesn't exist" is never a skip reason. Create the test data, run the
check, clean it up afterward.
</Aside>

## The `design` skill

Reach for `design` when building or changing any front-end surface —
components, layouts, pages, forms, flows, styles, or theme. It:

- **Builds to the project's design authority** — the plan's pinned `## Design Authority`
  (a customer mockup in *fidelity* mode, or the committed **brand guide** in *consistency*
  mode) — rather than inventing a second design language. The brand guide
  (`.kiro/context/brand-guide.md`) is the captured, reviewed source-of-truth.
- Enforces the **full component state set** for every component:
  - default
  - hover
  - focus
  - disabled
  - loading
  - empty
  - error

Loading, empty, and error are the three that hide dead-ends — a component that
only has its default state looks finished and isn't. `design` builds it right;
QA proves the states exist and lead somewhere.

## Design authority & the brand guide

A plan's UI can drift two ways — a build that **redesigns** a customer's provided look, or new UI
that ships **off-brand** from the rest of the app. Both used to pass QA. The design-fidelity thread
closes that, end to end:

- **`grill-me` pins a `## Design Authority`** for any UI plan — *fidelity* (reproduce the customer
  mockup's design language) or *consistency* (match the project brand guide). It pins the design
  **language** (tokens, component styling + states, layout, icon/motion); the **content** still
  evolves freely through grilling.
- **The `brand-guide` skill** captures the app's design language into a committed, reviewed
  `.kiro/context/brand-guide.md` — generated from the codebase design system crossed with the
  rendered app, with any inconsistencies surfaced for you to arbitrate. First run on a UI project
  prompts to generate it; it's the source-of-truth the `design` skill builds to.
- **QA enforces it.** For a UI change with a Design Authority, QA compares the rendered build's
  design language against the authority (token/component conformance, **not** a pixel diff — content
  differences don't count). A mismatch is a **FAIL that drives the normal QA↔mission fix loop**: the
  build is restyled to the authority and re-QA'd, and the mission can't clear until it conforms.

## Native mobile apps

A repo whose `qa-contract.json` has a `mobile` block is tested on real iOS and
Android devices through Mobile Next, not in a browser. The QA rules above still
hold (staging only, two-gate verdicts, screenshot evidence). Setup, the device
cost safeguards, and the limits are in [Mobile app QA](/workflows/mobile-qa/).
A mobile run writes `mobile` on line 2 of the `.qa-active` sentinel, which
marks it as a device run for the QA gates.

## Code-only work is a different lane

Work with no product surface — tooling, internal scripts, backend-only logic
with no UI impact — is verified by its own test suite (red-green: a failing
test that now passes, and the adjacent case re-checked), not by the browser
protocol above. Don't run a full QA reconciliation against product test
coverage for a change the product surface never touched.
