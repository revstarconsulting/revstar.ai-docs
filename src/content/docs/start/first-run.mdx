## Why you can't just run `kiro-cli`

A bare `kiro-cli` launch fails with:

```
profileArn is required
```

Kiro needs an AWS Identity Center (SSO) login before it can start a session,
and that login is scoped to a specific client. `kiroctl` supplies this by
launching through a **client-bound project** — a project directory tied to one
client's Identity Center configuration — rather than launching Kiro directly.

## Set up a client-bound project (terminal)

<Steps>

1. **Add the client.** This registers the client's Identity Center start URL
   and region:

   ```sh
   kiroctl client add --name "Acme" --idc-url https://acme.awsapps.com/start --region us-east-1
   ```

2. **Create the project**, bound to that client:

   ```sh
   kiroctl project new --dir ~/kiro/acme --client acme --scaffold
   ```

3. **Point QA at your environment** so a mission's `/qa` has a reachable target
   (without one it silently degrades):

   ```sh
   kiroctl project set-env --dir ~/kiro/acme \
     --base-url https://staging.acme.test --env staging --branch develop
   ```

   The GUI's new-project wizard has the same QA step; change these later per
   project via its **QA environment** card. This scaffolds
   `qa-contract.json` — see [QA & Design](/workflows/qa-and-design/#setting-up-qa-in-a-project).

4. **Open it.** This performs the client's Identity Center login and launches
   the session:

   ```sh
   kiroctl open --dir ~/kiro/acme --run
   ```

   This logs you in via SSO, then launches `kiro-cli chat --agent dev` inside
   the project directory.

</Steps>

## Ways to open a project

Setup is a one-time thing; opening a project is what you do every day. There are
three ways, and they all end up running the same `kiroctl open … --run` (SSO
enforced, repos ensured) — pick whichever fits how you work.

### From the desktop app (UI)

Double-click the **"RevStar.ai - New Project"** desktop icon (or run `kiroctl gui`).
The app is a two-pane, project-first layout:

- **Left — your projects.** Each row shows status badges at a glance: SSO
  **signed in** / **needs sign-in**, **ADO ready** / not set, and repos
  **present** / missing. Click a project to select it; a **filter** box narrows
  the list.
- **Right — the selected project's detail.** Everything about that project is
  inline-editable, no separate screens: **Client & sign-in** (IdC URL, region,
  AWS account, **Sign in** / **Re-authenticate**, and a "used by" note when the
  client is shared with other projects), **Azure DevOps** (RevStar ADO / the
  client's own ADO / none, org, project, a PM field, and the **PAT this project
  uses**), **Repos** (add by git
  URL or local path, with a **Browse…** picker; **Remove** shows a git-safety
  preview — dirty working tree, unpushed commits, no upstream — before it acts),
  and **QA environment** (staging URL, environment, target branch, backend
  access).

**New project** (top-right) opens a single guided wizard — Client → Project &
repos → Azure DevOps (RevStar / the client's own / none) → QA → Review → Create
→ Sign in → Launch. Nothing is written until you confirm on the Review step; if
a repo fails to clone during Create, you get a **Retry**.

The gear icon opens the **Settings** drawer: the default ADO org/PAT used by
new projects, your **saved PATs** (add, rename, replace the secret, or delete),
and any **unused clients**. Folders the app finds that aren't yet a project
show up under **Other folders found**, with a one-click **Set up**.

See the [Install & Setup guide](/start/install/#5-use-the-desktop-app) for the
full walkthrough.

### From the terminal dropdown or its desktop icon

When you create or open a project, Kiro registers **two per-project shortcuts** so
you can jump straight into that project:

- a **terminal dropdown entry** — a Windows Terminal profile, a macOS iTerm2
  dynamic profile, or a Linux applications `.desktop` entry; and
- a **"RevStar.ai - &lt;project&gt;" desktop icon**.

Either one opens *that* project directly in a terminal window (it runs
`kiroctl open --dir <dir> --run`, so the client's SSO is enforced). This is the
fastest way back into a project you work in often. Re-running the front-end
installer registers these for every existing project, too.

<Aside type="tip">
Missing the dropdown/icon (e.g. you cloned to a new location)? Re-register:
`bash tools/install-macos-frontend.sh` (macOS) / `bash tools/install-linux-frontend.sh`
(Linux) / `.\tools\New-KiroProject.ps1 -Install` (Windows).
</Aside>

### Terminal only

Skip the shortcuts and open from a shell — best for scripts, SSH sessions, or if
you live in the terminal:

```sh
kiroctl open --dir ~/kiro/acme --run
# or, from inside the project (--dir defaults to the current directory):
cd ~/kiro/acme && kiroctl open --run
```

<Aside type="note">
Each client is one AWS Identity Center boundary with its own isolated
credential store. Switching clients never mixes credentials — a project bound
to one client cannot authenticate against another.
</Aside>

## Multi-repo projects

A project can span **several repos** — a frontend and a backend, say — so one
Kiro session and one mission work across all of them. A project is a workspace
folder bound to one client, plus a `.kiro/repos.json` mapping of its repos. Each
repo is either **cloned** from a git URL into a workspace subfolder, or **linked**
(symlinked) from a clone you already have.

From the GUI (`kiroctl gui`): the new-project wizard's **Project & repos** step
adds one or more repos — each row is a **git URL** (cloned) or an **existing
local path** (linked); the project is created only once every repo is in
place. An existing project's **Repos** card has its own **Add repo** row for
attaching more later.

From the CLI:

```sh
kiroctl project add-repo --dir ~/kiro/acme --url git@github.com:org/frontend.git
kiroctl project add-repo --dir ~/kiro/acme --link /path/to/existing/backend
kiroctl project repos    --dir ~/kiro/acme
kiroctl open             --dir ~/kiro/acme --run   # clones any missing, then launches
```

A **single-repo** project opens the session **inside that repo**; a **multi-repo**
project opens at the workspace with each repo as a subfolder.

<Aside type="note">
Cloning private repos uses your **existing git/GitHub credentials** (SSH or
`gh`) — the client governs AWS/Kiro SSO, not GitHub. A URL with an embedded
credential is rejected. `open` clones only what's missing and never auto-pulls,
so it won't disturb a working tree.
</Aside>

## Orient in an existing codebase

When you link a repo you don't know, run the **`project-map`** skill once to build
a navigation map, so later sessions (and missions) jump straight to the right
files instead of re-scanning the tree:

> "map this project" · "audit the codebase" · "where is everything"

It writes a concise `.kiro/architecture.md` — stack, entry points, a directory
map, data models, routes, key modules, and the build/test/run commands — and
keeps a one-line pointer in project steering so it's read on demand. Re-run it
after a big structural change. For full shareable docs (ERD / API / rendered
diagrams), use the `kb` skill instead.
