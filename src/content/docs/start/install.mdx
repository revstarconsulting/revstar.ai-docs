## Fastest: the one-click installer

The quickest way to install RevStar.ai is the one-click installer on Mission
Control's **Developer Installers** page:

<LinkCard
  title="Mission Control → Developer Installers"
  description="Sign in with your @revstarconsulting.com Google account, then download the installer for your OS."
  href="https://revstarconsulting.net/dashboard/downloads"
/>

The page (also under the **SOP Wiki** menu) offers three installers, kept current
from the `v1` branch of the `revstar.ai` repo. Each tile shows the version (commit),
a **SHA-256** checksum and when it was last refreshed.

| Tile | File | Use it for |
| --- | --- | --- |
| **macOS** | `bootstrap-macos.sh` | A Mac. Installs everything natively. |
| **Windows** | `bootstrap-windows.ps1` | A Windows PC without WSL yet. Sets up WSL, then everything inside it. |
| **WSL / Linux** | `bootstrap-wsl.sh` | An existing WSL (Ubuntu) or native Linux shell. |

<Aside type="caution" title="You still need GitHub access">
The installer downloads RevStar.ai's two private repos (`revstar.ai` and
`revstar.ai-registry`), so your machine needs a **GitHub account in the RevStar org**
and **git**, signed in once with `gh auth login` (or an SSH key loaded with
`eval "$(ssh-agent -s)" && ssh-add`). Without it the installer stops with
**BLOCKED: could not clone…** and the exact fix — it never half-installs.
</Aside>

<Tabs syncKey="os">
  <TabItem label="macOS" icon="apple">
    <Steps>

    1. Download **macOS** from the Downloads page.
    2. Optional: check the file matches the SHA-256 shown on the tile:
       `shasum -a 256 ~/Downloads/bootstrap-macos.sh`
    3. In **Terminal**:
       ```sh
       bash ~/Downloads/bootstrap-macos.sh
       ```
       It installs only what's missing: `fnm` (per-user, no Homebrew), Node LTS,
       `kiro-cli`, then clones `revstar.ai` and `revstar.ai-registry` into your home
       folder (`~/revstar.ai`, `~/revstar.ai-registry`) and runs the pack installer.

    </Steps>
  </TabItem>
  <TabItem label="Windows" icon="seti:windows">
    <Steps>

    1. Download **Windows** from the Downloads page.
    2. Optional: check the checksum in PowerShell:
       `Get-FileHash $HOME\Downloads\bootstrap-windows.ps1 -Algorithm SHA256`
    3. In **PowerShell**:
       ```powershell
       powershell -ExecutionPolicy Bypass -File $HOME\Downloads\bootstrap-windows.ps1
       ```
       It asks for administrator rights (needed to install WSL), installs WSL and
       Ubuntu, then tells you what to do next:
       - **If Windows needs a reboot**, reboot first.
       - **Open Ubuntu** from the Start menu. The first launch asks you to create
         your Linux username and password.
    4. In the Ubuntu window, run the **Stage 2** command the script printed:
       ```sh
       git clone --branch stable https://github.com/revstarconsulting/revstar.ai.git ~/revstar.ai \
         && cd ~/revstar.ai && ./scripts/bootstrap-wsl.sh
       ```
       (The script prints the exact command. Run it with `-Channel beta` and it
       prints the beta one instead: `--branch v1` and `KIRO_CHANNEL=beta`. See
       [Release channels](#release-channels--stable-vs-beta).)
       That installs Node, `kiro-cli`, the registry and the pack inside WSL. (Run
       `gh auth login` in Ubuntu first if the clone is refused.)

    </Steps>
    RevStar.ai runs inside WSL from then on — use the Ubuntu terminal for
    `kiroctl` and `kiro-cli`.
  </TabItem>
  <TabItem label="WSL / Linux" icon="linux">
    <Steps>

    1. Download **WSL / Linux** from the Downloads page. On WSL the file lands in
       Windows' Downloads folder: `/mnt/c/Users/<you>/Downloads/`.
    2. Optional: `sha256sum <path>/bootstrap-wsl.sh` and compare with the tile.
    3. In your WSL / Linux shell:
       ```sh
       bash /mnt/c/Users/<you>/Downloads/bootstrap-wsl.sh     # WSL
       bash ~/Downloads/bootstrap-wsl.sh                      # native Linux
       ```
       It installs `fnm`, Node LTS and `kiro-cli` if missing, clones `revstar.ai` and
       `revstar.ai-registry` into your home folder, and runs the pack installer.
       Add `--enable-passwordless-sudo` to opt in to passwordless sudo (see below).

    </Steps>
  </TabItem>
</Tabs>

**Every installer** is safe to re-run (it only fills in what's missing and pulls
updates), accepts `--dry-run` (`-DryRun` on Windows) to preview, and ends with the
pack's own self-test (`selftest PASSED`).

**When it finishes:**

<Steps>

1. Open a **new** terminal so `fnm`, Node and `kiro-cli` are on your `PATH`.
2. Sign in to Kiro if prompted (`kiro-cli login`, a one-time step).
3. Sign in to Mission Control: run `kiroctl gui` and click **Sign in with Mission
   Control** — Kiro agent sessions need it (see [§5e](#5e-sign-in-to-mission-control)).
   The installer tells you if you're not signed in yet.
4. Check the install: `kiroctl doctor` and `kiroctl telemetry status` should show no
   `FAIL` or `[action]` lines.
5. If something's wrong, open the app's **Settings → Diagnostics**, click **Run
   diagnostics**, and send the copied report to the RevStar.ai maintainer.

</Steps>

Already installed? Don't re-download — run `kiroctl update` to get new versions
(see [Updating later](#6-updating-later)).

The scripts behind the Downloads page are the same ones in the repo's `scripts/`
folder, so the clone-based steps below are equivalent.

## 0. One-shot bootstrap (new / near-bare machine)

If the machine doesn't yet have Node, Kiro CLI (or, on Windows, WSL), use the
**bootstrap** scripts — they install the prerequisites (via `fnm` for a pinned
Node LTS, the official `kiro-cli` installer) and then run the pack installer for
you. Everything is **idempotent** (re-running only fills what's missing) and
**detect-and-report** (a blocked prerequisite is reported with the fix, never a
half-install).

<Aside type="note" title="Download needs GitHub access (the repo is private)">
`revstar.ai` is a **private** repo, so there is no anonymous `curl | bash` — the
download is authenticated. You need a **GitHub account added to the RevStar org**
and **git** (ships with macOS Command Line Tools and inside WSL). Sign in once
with `gh auth login` or your SSH key, then clone and run the bootstrap below.
</Aside>

<Tabs syncKey="os">
  <TabItem label="macOS" icon="apple">
    ```sh
    # git comes from the Command Line Tools (xcode-select --install) if missing
    git clone --branch stable https://github.com/revstarconsulting/revstar.ai.git
    cd revstar.ai
    ./scripts/bootstrap-macos.sh              # arms the default gates; --arm-safe is accepted and does the same
    ```
    No Homebrew required — `fnm` installs Node per-user.
  </TabItem>
  <TabItem label="Linux / WSL" icon="linux">
    ```sh
    sudo apt-get update && sudo apt-get install -y git   # if git is missing
    git clone --branch stable https://github.com/revstarconsulting/revstar.ai.git
    cd revstar.ai
    ./scripts/bootstrap-wsl.sh                # add --enable-passwordless-sudo to opt in (below)
    ```
  </TabItem>
  <TabItem label="Windows" icon="seti:windows">
    A bare Windows box has no git yet, so grab just the Stage-1 script from the
    GitHub web UI (signed in): open
    [`scripts/bootstrap-windows.ps1`](https://github.com/revstarconsulting/revstar.ai/blob/v1/scripts/bootstrap-windows.ps1)
    and click **Download raw file**, then run it in an **elevated** PowerShell:
    ```powershell
    .\bootstrap-windows.ps1
    ```
    Stage 1 installs WSL (+ a distro). If Windows needs a reboot it tells you;
    otherwise launch the distro once (to create your Linux user). Then run the
    **Stage-2** command it prints inside WSL — a clone + `bootstrap-wsl.sh`:
    ```sh
    git clone --branch stable https://github.com/revstarconsulting/revstar.ai.git ~/revstar.ai \
      && cd ~/revstar.ai && ./scripts/bootstrap-wsl.sh
    ```
  </TabItem>
</Tabs>

<Aside type="note" title="Pick the channel: stable by default">
The bootstrap clones **both** repos on the branch for your [release channel](#release-channels--stable-vs-beta):
`stable` (the default) or `v1` for beta. Choose beta with `KIRO_CHANNEL=beta` in front of the
script (macOS, Linux / WSL) or `-Channel beta` on `bootstrap-windows.ps1`. The GitHub default
branch is `v1`, so a plain `git clone` with no `--branch` lands on beta; that is why the
commands above name `stable`. `KIRO_PACK_BRANCH` and `KIRO_REGISTRY_BRANCH` override the branch
for one repo. Running a bootstrap again on a clone that already exists only fast-forwards it
and does not switch branches; use `kiroctl update` for that (see
[Updating later](#6-updating-later)).
</Aside>

<Aside type="tip" title="Already signed in with gh? Grab a single script without a full clone">
With `gh` installed and authenticated you can pull just one bootstrap script:

```sh
gh api repos/revstarconsulting/revstar.ai/contents/scripts/bootstrap-macos.sh \
  -H "Accept: application/vnd.github.raw" > bootstrap-macos.sh && bash bootstrap-macos.sh
```
</Aside>

<Aside type="caution" title="Passwordless sudo — opt-in, security tradeoff">
A fully autonomous mission runs commands non-interactively, so a `sudo` that
prompts for a password will **hang** (there's no TTY to answer it). You can
grant passwordless sudo so missions don't stall:

```sh
./install.sh --enable-passwordless-sudo        # or: ./scripts/enable-passwordless-sudo.sh
```

This writes a `visudo`-validated `/etc/sudoers.d/90-revstar-kiro` after you
confirm. **`NOPASSWD` means this user can run `sudo` with no password** — fine on
a personal dev box, but it may violate policy on a shared/corp machine, so it is
**opt-in and never applied by the default install**. Scope it with
`--commands "apt-get,systemctl"` instead of all commands, and undo any time with
`sudo rm /etc/sudoers.d/90-revstar-kiro`. `kiroctl doctor` tells you whether sudo
will prompt (and so whether missions would hang).
</Aside>

Already have Node + Kiro CLI (+ WSL on Windows)? Skip to the manual steps below.

## 1. Prerequisites

- **Node.js 18+**
- **git** with access to the private repos (SSH key or `gh` login)
- **[Kiro CLI](https://kiro.dev)** (`kiro-cli`) installed and on your `PATH`
- **Windows only:** WSL2 with a Linux distro (the CLI runs inside WSL)

## 2. Get the two repos

RevStar.ai ships as two repos, cloned **side by side**:

```sh
git clone --branch stable https://github.com/revstarconsulting/revstar.ai.git
git clone --branch stable https://github.com/revstarconsulting/revstar.ai-registry.git
```

For the beta channel, use `--branch v1` on both instead.

`revstar.ai` holds the `kiroctl` CLI and installers; `revstar.ai-registry` holds the
content pack (agents, skills, gates, steering).

<Aside type="caution" title="Use git clone — not a “Download ZIP”">
A GitHub ZIP download strips the executable bits off the installer scripts and
gives you no `kiroctl update` path — a zip-based install **silently skips the
desktop launcher**. Always `git clone`.
</Aside>

<Aside type="tip" title="Let your Kiro do it">
You can hand this to an existing Kiro session:

> `git clone --branch stable` https://github.com/revstarconsulting/revstar.ai.git and
> https://github.com/revstarconsulting/revstar.ai-registry.git side by side, then from
> inside `revstar.ai` run the installer for my OS with
> `KIRO_REGISTRY_ROOT=../revstar.ai-registry`. Then verify with `kiroctl doctor` and
> `kiroctl doctor --governance`. Don't commit any secrets.
</Aside>

## 3. Run the installer

From inside `revstar.ai`, point the installer at your `revstar.ai-registry` clone:

<Tabs syncKey="os">
  <TabItem label="macOS" icon="apple">
    ```sh
    KIRO_REGISTRY_ROOT=../revstar.ai-registry ./installers/install-macos.sh
    ```
  </TabItem>
  <TabItem label="Linux" icon="linux">
    ```sh
    KIRO_REGISTRY_ROOT=../revstar.ai-registry ./installers/install-linux.sh
    ```
  </TabItem>
  <TabItem label="Windows" icon="seti:windows">
    Run in PowerShell (it provisions the WSL side and the Windows launcher):
    ```powershell
    $env:KIRO_REGISTRY_ROOT="..\revstar.ai-registry"
    .\installers\install-windows.ps1
    ```
  </TabItem>
</Tabs>

Every install arms five hooks: the four **safe gates** (`mission-inject`, `mission-turn-recorder`,
`session-context`, `update-notify`) and, since 0.11.0, `mission-state-protect`. The four safe
gates can't block anything: they inject mission and session context, remind you of updates,
and record the turn receipts that measure a mission's autonomous hours.
`mission-state-protect` refuses an agent's edits of mission state. `--arm-safe` is still
accepted and does the same. **0.11.0 (beta).** The blocking gates other than
`mission-state-protect` stay inert until you arm them. To keep one of the five off for good,
create `~/.kiro/gates/<name>.disabled`; installs and `kiroctl update` never re-arm it. See
[Gates → The gates armed by default](/capabilities/gates/#the-four-safe-hooks-are-armed-by-default).
`install.ps1` arms the same five. To arm every gate at once, run `./install.sh --arm-all`
(`.\install.ps1 -ArmAll` on Windows). **0.11.0 (beta).** That now includes `ado-receipt-gate`,
which stays off in a plain install or `kiroctl update`.

### What the bootstrap does

1. Copies `steering/` and `skills/` from the registry into `$KIRO_HOME`.
2. Writes the `dev`, `coder`, and `scout` agent configurations.
3. Sets `chat.defaultAgent` to `dev`.
4. Asserts the model pins (Opus for `dev`, Sonnet for `coder`/`scout` — never
   Haiku, never `auto`).
5. Runs the governance guard against the registry's rules.
6. Wires the Playwright and Azure DevOps MCP servers.
7. Links the `kiroctl` binary onto your `PATH` and installs the desktop launcher.
8. Records an install manifest so `kiroctl doctor`/`kiroctl update` know the layout.
9. **0.11.0 (beta).** Turns kiro-cli Workflows off (`chat.enableWorkflows` is set to `false` in `~/.kiro/settings/cli.json`), because a `/goal` workflow skips the pack's hooks. `kiroctl update` does the same.
10. **0.11.0 (beta).** Writes the global hook file `~/.kiro/hooks/revstar-workbench.json`. It runs `mission-pause`, `mission-state-protect` and `git-protect-gate` for any agent that isn't `dev`, `coder` or `scout`. See [Gates → The global hook](/capabilities/gates/#the-global-hook).

## 4. Verify

```sh
kiroctl doctor
node ../revstar.ai-registry/kiro/gates/selftest.js
kiroctl doctor --governance
```

`kiroctl doctor` reports the install is healthy; the gate selftest prints
`N/N passed` and every case must pass; governance reports **OK**.

## 5. Use the desktop app

Everything day-to-day happens in the **RevStar.ai project GUI** — one identical local
web app on macOS, Windows and Linux. Launch it from the **“RevStar.ai - New Project”**
desktop icon the installer created — it now carries the **RevStar brand icon** on all
three platforms (a `.desktop` entry on Linux, an app bundle on macOS, a `.lnk` on
Windows) — or run:

```sh
kiroctl gui
```

It opens in your default browser on `127.0.0.1` (loopback only, gated by a
per-launch token). The app is a **two-pane, project-first** layout: your
projects on the left, the selected project's editable detail on the right.

### 5a. The project list and status badges

The left pane lists every project you've created, each with three status
badges so you can see what needs attention without opening it:

- **SSO** — signed in, or needs sign-in.
- **ADO** — ready, or not set up.
- **Repos** — present, or one or more missing.

A **filter** box at the top narrows the list as you type. Click a project to
load its detail on the right. Folders on disk that look like projects but
aren't registered yet appear below the list under **Other folders found**,
each with a one-click **Set up**.

### 5b. Edit a project in place

Selecting a project shows its full detail on the right, split into
inline-editable sections — no separate screens, no re-running a wizard to
change something:

<Steps>

1. **Client & sign-in** — the client's Identity Center start URL, region, and
   AWS account; **Sign in** or **Re-authenticate**; and, when the client is
   shared, which other projects use it.
2. **Azure DevOps** — the board mode (**RevStar ADO**, the **client's own
   ADO**, or **none**), the org URL, the ADO project, the project manager
   (a typeahead against your ADO project's members where a PAT allows it,
   otherwise free text), and the **PAT this project uses** — pick any saved PAT
   or **none**. Org, project and PM apply to the client (and any projects that
   share it); the PAT binds this project only. Manage saved PATs in **Settings**.
3. **Repos** — every repo in the project, added by **git URL** (cloned) or
   **local path** (linked, with a **Browse…** picker). **Remove** first shows a
   git-safety preview — a dirty working tree, unpushed commits, or no
   upstream — so you don't lose work by accident.
4. **QA environment** — staging URL, environment, target branch, and optional
   backend access, kept in sync with the project's `qa-contract.json`.

</Steps>

<Aside type="caution" title="Cloning uses your own git credentials">
Private-repo clones use your existing git/GitHub credentials (SSH or `gh`). A URL
with an embedded credential (`https://user:token@…`) is **rejected** — use SSH or
a credential helper.
</Aside>

### 5c. Create a project — the guided wizard

The **New project** button (top-right) opens a single guided wizard:

**Client → Project & repos → Azure DevOps (RevStar / client's own / none) → QA
→ Review → Create → Sign in → Launch**

Nothing is saved until you confirm on the **Review** step — Create then writes
everything at once. If a repo fails to clone, you get a **Retry** rather than a
half-created project.

### 5d. Settings and Azure DevOps PATs

The gear icon opens the **Settings** drawer:

- **Default ADO** — the org/PAT new projects default to when they pick RevStar ADO.
- **Saved PATs** — add, rename, replace the secret on, or delete a PAT. A PAT
  is saved once and reused across every project that needs it; it's stored in
  your OS keychain (with a `0600`-file fallback) and never shown back or
  written to config.
- **Mission Control** — sign in / sign out, and the **Connection** health rows
  (sign-in, telemetry, queue, project) with **Check now**. See
  [Sign in to Mission Control](#5e-sign-in-to-mission-control).
- **Gates** — **0.11.0 (beta).** An **ADO receipt gate** checkbox, off by default, with its status
  (armed, off by choice, not armed). Only a person can change it. See
  [Gates](/capabilities/gates/#the-ado-receipt-gate-in-the-app).
- **Unused clients** — clients no projects currently use, with a one-click delete.

<Aside type="tip">
Prefer the CLI? `kiroctl client set-pat --slug <client>` reads the PAT from stdin
(never the argument list).
</Aside>

Each project also has a **Report a bad run** action, for flagging a session
that went wrong.

### 5e. Sign in to Mission Control

Kiro agent sessions (`dev`, `coder`, `scout`) need a **Mission Control sign-in** —
it powers RevStar SOP standards and adoption telemetry. Until you sign in, the app
shows a red **Critical — not signed in to Mission Control** banner and every prompt
is refused with the same instruction.

Click **Sign in with Mission Control** (the banner, or Settings → Mission Control),
finish the Google sign-in in your browser with your `@revstarconsulting.com`
account, and you're done — the sign-in lasts a year and refreshes silently. Sign-in
is in the app only; there is no terminal sign-in command.

If a repo matches more than one of your Mission Control projects, the app asks
once which one it is for. No browser on the machine, or Mission Control down? See
the [time-limited bypass](/capabilities/gates/#mission-control-sign-in).

## 6. Updating later

```sh
kiroctl update
```

A verified pull of both repos + reinstall — bolt-on, never subtract, so your own
customizations are preserved. Both repos are put on your channel's branch first
(`stable`, or `v1` for beta), then fast-forwarded. It never stashes, resets or forces
anything: uncommitted changes to tracked files, or local commits that aren't on the
remote branch, stop the update with a message and change nothing.

| Flag | What it does |
| --- | --- |
| `--check` | Report whether an update is available; change nothing. |
| `--channel <beta\|stable>` | Switch to that [release channel](#release-channels--stable-vs-beta) and remember it. |
| `--yes` | Answer yes to the "Move back to stable?" question below without asking. |
| `--registry <path>` | Point at the registry clone if it moved since install. |
 Restart your Kiro session afterward so steering,
skills and MCP servers reload. (On Windows, run it inside WSL.)

If you aren't signed in to Mission Control yet, the update ends by opening the
RevStar.ai app on its sign-in banner (or, with no display or `KIRO_NO_GUI=1`, by
printing the one step to take).

## Release channels — stable vs beta

RevStar.ai ships on two channels:

- **`stable`** — the **default for a new install**. A vetted line, promoted from
  beta only after a full QA pass. This is what you get unless you ask otherwise.
- **`beta`** — the active line where new features land first. Opt in at install
  time:

  ```sh
  ./install.sh --channel beta          # macOS / Linux / WSL
  .\install.ps1 -Channel beta          # Windows PowerShell
  ```

  (and `--channel stable` / `-Channel stable` is always available to be explicit).

The channel is recorded in `kiroctl-install.json`, and `kiroctl update` then pulls
that channel's line — so a stable install stays on stable and a beta install stays
on beta, with no flags to remember. **Re-installing keeps the channel you already
have** unless you pass `--channel`, so updating in place never moves you between
channels. `kiroctl version` and `kiroctl doctor` show your current channel and
version, and the GUI header shows them too.

<Aside type="note">
**0.11.2.** An install made before channels existed, with no channel recorded, follows the branch its clone is on
(`v1` is beta, `stable` is stable), and stable when there is no clone to read. Before 0.11.2 the updater read a
missing channel as beta while the installer recorded stable, so such an install could run beta code labelled
stable. New features land on **beta** first; anything not yet promoted to stable is marked *beta* on the page.
Switch channels with `kiroctl update --channel beta` or `kiroctl update --channel stable` (or by re-installing
with `--channel`).
</Aside>

### Nothing moves you between channels by itself

**0.11.2.** Only `--channel` changes your channel:

- `KIRO_CHANNEL` set to a different channel than the one recorded is refused, naming both. Before, it switched
  the clones to the other line without recording it.
- An update run without a terminal (from the app or a script) on a stable install whose clone sits on `v1` is
  refused with **UPDATE NOT APPLIED** and both fixes: `kiroctl update --channel stable` puts the clone back on
  stable, `kiroctl update --channel beta` keeps beta on purpose. Before, it quietly switched the install to beta.
- A channel value other than `beta` or `stable` (any case) is refused, never read as beta.
- `kiroctl doctor` has a **channel-code** row. It FAILs when an install says stable but runs beta code, including
  an install that is a plain copy rather than a git clone, and the app header says
  *stable (running beta code)*.
- The bootstrap scripts put an existing clone on its channel's branch (fast-forward only) instead of pulling
  whatever branch it is on.

### A channel is a branch

Both repos, `revstar.ai` and `revstar.ai-registry`, have a `stable` branch and a
`v1` branch. The channel only means something if your clones are on its branch:

| Channel | Branch (both repos) |
| --- | --- |
| `stable` | `stable` |
| `beta` | `v1` |

Older bootstrap scripts cloned the default branch, `v1`, so a "stable" install could be
running beta code without saying so. Now:

- **`kiroctl update`** puts both repos on the channel's branch and then fast-forwards
  them. If a repo has uncommitted changes to tracked files, or has diverged from the
  remote branch, it stops and changes nothing; fix that yourself and run it again.
- **A stable install found on `v1`** is never moved silently, because that drops beta
  features. At a terminal, `kiroctl update` asks
  `Move back to stable? This drops beta features. [y/N]`. Answer **n**, or run it where
  there is no terminal (the app's update, for example), and it stays on `v1` and records the
  channel as **beta**, so `kiroctl version` tells the truth. `kiroctl update --yes` says yes
  for you.
- **`kiroctl doctor`** has a `channel-branch` row. It warns when a checkout isn't on its
  channel's branch and prints the command that fixes it.

```sh
kiroctl update --channel stable        # asks first if it would leave beta behind
kiroctl update --channel stable --yes  # move without asking
kiroctl update --channel beta
```
